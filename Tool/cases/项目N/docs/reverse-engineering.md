## 1. 保护层分析

### 1.1 L3 — 程序集代码加密（完整算法还原）

目标 PE 中名为随机字节的节区被整体 XOR 加密，**密钥由其它节区的内容哈希派生**
（这同时构成反篡改机制：改动别的节区会导致本区解不开）。

**节区识别**

```
节名前 8 字节 = 两个 uint32，其乘积
    == 0x65452714  →  目标加密节区
    != 0 且 != magic →  参与密钥种子演化（反篡改校验源）
```

**密钥派生**

```
种子初值：  num5..num8 = 1758353659, 186699061, 1283470176, 872273121

内容哈希演化（逐 dword，遍历所有非目标、非空节区）：
    nv = (num5 ^ v) + num6 + (num7 * num8)
    num5, num6, num7, num8 = num6, num7, num8, nv

展开 16 项 keystream：
    for j in 0..15:
        arr[j]  = num8;  arr2[j] = num6
        num5 = ROL(num6, 27); num6 = ROL(num7, 29)
        num7 = ROL(num8, 25); num8 = ROL(num5, 21)
    for i in 0..15:
        arr[i] = arr[i] XOR arr2[i]   (i % 3 == 0)
               = arr[i] MUL arr2[i]   (i % 3 == 1)
               = arr[i] ADD arr2[i]   (i % 3 == 2)
```

**逐 dword 解密**

```
plain        = cipher ^ ks[i & 15]
ks[i & 15]   = (ks[i & 15] ^ plain) + 1204611781      ← 自反馈常数
```

> **关键性质**：keystream 以**明文**推进，因此"解密 → 改字节 → 加密"可产出
> **除补丁点外与原文件逐字节一致**的输出。这是后续微创补丁的基础。

### 1.2 L4 — 代码虚拟化 VM（三层全破）★ 核心

VM 保护由三层嵌套构成：

```
┌─ PE 资源（754,692 B = "VGJN" + 2948 × 256 B）
│
├─[第 1 层] RSA-2048 / PKCS#1 v1.5
│      n = a1(128B FieldRva) ‖ Convert.FromBase64String(内嵌字符串)(128B)
│      e = 65537；块长 256 B，每块明文 245 B（PKCS#1 固定 8 字节填充）
│      → 2948 × 245 = 722,260 B
│      ★ 离线 pow(c, e, n) 与客户端运行时流**逐字节一致**（已交叉验证）
│
├─[第 2 层] 位置流 XOR
│      seed = seedArg ^ (-559030707)        seedArg(VM流) = 1822868938
│      plain[i] = cipher[i] ^ (byte)(seed ^ i)
│      → 722,260 字节 VM 字节码**全量解密**（熵 7.9997 → 6.7565）
│
└─[第 3 层] 方法寻址（名称即自描述令牌）
       存根名（11 字符左右的不可读串）
         → Ascii85 解码（字母表 '!'..'u'，K = {85⁴, 85³, 85², 85, 1}）
         → 位置流 XOR 解密（seedArg = 1485391981）
         → 乱序 ReadInt64 → VM 流偏移
         → 该处方法记录：[18B 头][len][方法名][u32 代码长度][4 字节定长指令流]
       ★ 运行时探针与离线复算 **7/7 精确命中**；编码**完全可逆**
```

**方法记录格式**

```
偏移 +0x00  18 字节记录头（签名 / 类型描述）
偏移 +0x12  [1 字节长度][方法名 ASCII]
偏移 +…     [u32 代码长度][代码区]
```

指令为 **4 字节定长 token**；已识别 `0x42487a8f` = `ret`，
`0x5d914689` / `0xb4f09a23` = 取 `this` / 字段访问类。

**成果**：VM 字节码全量明文（3,917 成员记录 / 7,107 条可打印串，类型名与方法名全部可读）。

### 1.3 L5 — 自定义对称密码（完整还原）

| 组件 | 还原内容 |
|:---|:---|
| 分组 / 密钥 / 模式 | 32-bit 分组 / **80-bit 密钥** / ECB / **12 轮** |
| 轮函数 | 256 字节 **S-box** 混淆查表：<br>`b5 = S[lo ^ k[(4·sum+0)%10]] ^ hi`<br>`b7 = S[b5 ^ k[(4·sum+1)%10]] ^ lo`<br>`b8 = S[b7 ^ k[(4·sum+2)%10]] ^ b5`<br>`b9 = S[b8 ^ k[(4·sum+3)%10]] ^ b7` |
| 轮调度 | `decrypt: delta=+1, sum=0`；`encrypt: delta=-1, sum=23` |
| 级联 | `SymmetricAlgorithm[5]`，每级由 KDF 派生 **10 B 密钥 + 4 B IV**（共 70 B） |
| KDF | `DeriveBytes(password, salt, iterationCount=1)` |

> 该密码用于业务数据通道，**不是** VM 字节码的封装层（VM 流为纯 RSA）。

## 3. 缺陷分析（4 类）

### 3.1 缺陷一 · PRO 权益本地化裁决（CWE-602）

全部功能设置项（26 项）中有 **4 项**在构造时被打上"PRO 专属"标记：

```
IL（设置项构造）:
    ldc.i4.1                        ; true = "需要 PRO"
    call  <PRO 标记写入方法>
```

另有一个**全局授权态查询入口**（`isPro()` 等价物），被 **8 处**托管调用点引用：

| 调用点 | 语义 |
|:---|:---|
| 激活页状态机 | `激活成功 && isPro()` → 显示"已激活" |
| 优化流程 | `isPro() && Key 为空` → 直接判定任务完成（跳过执行） |
| 优化流程 | `!isPro() \|\| Key.<条件>` → 执行实际任务 |
| 页面 ViewModel | `IsEditable && isPro()` → 调整项可编辑性 |
| 设置列表构建 | 决定列表项可用性 |
| 页面级闸门 ×3 | 若干模块可见性 |

**核心问题**：权益判定不依赖任何服务端签发的凭据 → 客户端既是运动员又是裁判。

### 3.2 缺陷二 · 授权校验 Fail-Open 短路（CWE-287）★

授权装载状态机中的唯一判定点：

```
call  <凭据空值检查>          ; "Key 是否为空 / null 字符串"
brtrue.s  +offset             ; 非空 → 跳过服务端校验
```

凭据空值检查的语义：

```
null  /  ""  /  "null"   →  true   (视为"无需校验")
其它任意字符串            →  false  (必须联网校验)
```

**即：把凭据置空或写成 `"null"`，客户端就自认授权校验"通过"，完全不发请求。**

这是典型的 **Fail-Open**：把"无法判定"当作"判定通过"。

**副作用观察**：该旁路可使客户端"自认通过"，但**不足以点亮首页 PRO 徽章**
（徽章状态依赖服务端响应内容），且部分流程会抛 `IndexOutOfRangeException`。
因此它主要作为**授权体系设计缺陷的证据**，而非完整的权益解锁手段。

### 3.3 缺陷三 · 特权状态用户可写（CWE-863）

71 个功能开关以**明文布尔值**存放于 `HKCU`，任何用户态进程均可读写，
客户端读取后未做任何完整性/来源校验。

**无需修改二进制**，仅靠配置写入即可改变功能行为。

### 3.4 缺陷四 · 明文传输 + 硬编码密钥（CWE-319 / CWE-798）

| 问题 | 影响 |
|:---|:---|
| 授权接口走明文 HTTP | 中间人可窃听 / 篡改 |
| 硬编码 AES-128 密钥（随包分发） | 可离线解密历史流量并伪造授权响应 |
| 固定 64 字节前缀 | 便于流量识别与重放 |
| 裸 IP 兜底地址 | 域名封锁后仍可通信，扩大攻击面 |

## 5. 加固建议

| 层级 | 措施 |
|:---|:---|
| **架构** | 确立"服务端权威"：客户端只持有并呈递凭据；核心权益资源由服务端加密下发 |
| **鉴权逻辑** | 全面改为 **Fail-Closed**：凭据缺失/为空/非法一律判定失败 |
| **凭据形态** | 改用非对称签名凭据（Ed25519 / RSA-PSS），绑定硬件指纹 + 有效期 + 可吊销 |
| **传输层** | 全链路 HTTPS + 证书绑定；移除裸 IP；Nonce + 时戳 + 请求签名防重放 |
| **密钥管理** | 移除随包分发密钥，改为会话协商临时密钥（ECDH）+ 服务端签名 |
| **本地状态** | 本地配置仅作"用户偏好"，**不得作为权益判据** |
| **运行时** | 现有反篡改机制应"解不开即拒绝运行"，而非静默降级 |

## 6. 关键教训

> ### 📌 保护层强度 ≠ 安全架构
>
> 项目N 使用了商业级混淆 + 代码虚拟化，把静态分析成本从"小时级"提升到"天级"。
> 但审计证明：**只要架构层存在"裁决权在客户端"的根本缺陷，最终仍会被突破。**
>
> 虚拟化保护的常见可还原特征：
> 1. **方法名自描述令牌** —— 名称本身编码了方法在字节码流中的位置；
> 2. **位置相关的流加密** —— keystream 仅与偏移相关，与内容无关；
> 3. **封装层可分离** —— 非对称封装（RSA）与外层流加密可被独立剥离。
>
> 一旦识别出上述特征，整条保护链可被**系统性还原**，而非逐点对抗。
