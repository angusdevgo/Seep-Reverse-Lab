# Agent Note: 加密代码节区的微创补丁策略

Status: implemented

## Problem

项目N 的授权判定逻辑全部位于**被整体加密的代码节区**内。
若要在不改动产品行为的前提下验证授权缺陷，需要：

1. 在**明文 IL 层**精确改写少数几个字节；
2. 产出的文件要尽可能**接近原版**，以降低触发完整性自校验的风险；
3. 补丁要可重复生成（从原版样本出发，结果确定）。

难点：该加密方案带**自反馈**——keystream 的推进依赖已解出的明文，
因此"改一个字节"会使其后所有密文**雪崩**。
朴素的"解密→改→原样加密"会产生一个与原版大量字节不同的文件。

## Decision

采用**按加密方向回写 + 逐点原始字节校验**的微创补丁策略：

1. 复现加密方案，**静态派生** 16 项 keystream；
2. 将目标节区**解密到明文 IL 层**；
3. 在明文层改写目标字节，并**逐点校验原始字节是否匹配**（不匹配即中止）；
4. 用**加密方向**重新加密回写。

第 4 步的关键：keystream 的推进在解密与加密两个方向上都使用**明文**：

```
plain      = cipher ^ ks[i & 15]
ks[i & 15] = (ks[i & 15] ^ plain) + FEEDBACK
```

因此加密方向与解密方向可以共用同一个推进函数（仅输出不同），
从而保证**除补丁点外，输出文件与原文件逐字节一致**。

同时固化两条纪律：

- **补丁点必须逐点校验原始字节**：脚本打印每个补丁点的"原始字节 → 新字节"，
  并标记是否匹配。任一不匹配即视为样本版本不符，中止执行。
- **补丁按 profile 分组**：`flags`（仅权益标记）/ `pro`（+主开关）/
  `max`（+授权旁路）。每组可独立生成，便于做对照实验。

## Alternatives considered

- **整体重打包（反编译 → 修改 → 重新编译程序集）** ——
  最强理由：改动最直观，不需要理解加密方案，且能实现任意复杂度的逻辑修改。
  否决原因：重新编译会改变元数据布局、方法体偏移与节区结构，
  **必然触发完整性自校验**；实测该路径会直接导致程序集加载失败。

- **运行时内存补丁（注入后改写内存中的判定）** ——
  最强理由：完全绕过静态加密与完整性校验，改动不落盘。
  否决原因：需要注入/调试器环境，不适合作为**可重复、可交付**的验证手段；
  且本案例的目标是证明"静态二进制也可被篡改"，运行时补丁会削弱这一论点。

- **不改二进制，只靠配置文件触发缺陷** ——
  最强理由：零风险，不需要理解任何加密方案。
  否决原因：只能覆盖"特权状态可写"与"授权旁路"两类缺陷，
  无法证明"PRO 权益判定可被二进制级改写"这一核心论点。故两者并行。

## Consequences

- **收益**：产出的补丁版样本**除补丁点外与原版逐字节一致**，
  最大程度降低被反篡改机制发现的风险。
- **收益**：补丁脚本可**从原版样本重复生成**，结果确定，
  满足可复现性门禁（多次执行结果一致）。
- **代价与已知上限**：差异字节数在输出统计中仍然很大（数万至二十余万），
  这是 keystream 自反馈导致的**密文雪崩**，属正常现象。
  因此**不能用"差异字节数"判断补丁正确性**，必须看**补丁点校验结果**与**探针结果**。
  这一点已写入交付文档的注意事项。
- **代价**：该策略只能做**等长或更短**的改写（不得改变节区大小）。
  需要更大改动时必须走"替换非对称封装公钥"路径。

## Verification

- 补丁脚本对每个补丁点打印原始字节与新字节，全部显示校验通过；
- 反射探针独立进程验证：原版 `False` → 补丁版 `True`；
- 对照组（仅权益标记、不改主开关）保持 `False`，
  证明补丁作用域精确、无越界副作用。
