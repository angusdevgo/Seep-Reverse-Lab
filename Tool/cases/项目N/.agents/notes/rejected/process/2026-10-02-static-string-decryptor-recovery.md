# Agent Note: 静态还原字符串解密器

Status: rejected — 控制流混淆过重，静态还原投入产出比不可接受；已改用运行时反射转储

## Problem

目标程序集的字符串常量全部加密，需要还原约 7800 条明文以支撑后续分析。
最直接的想法是静态还原解密器本身。

## Proposal

静态分析字符串解密方法，还原其算法（密钥派生、索引映射、解码变换），
然后在离线环境批量解密全部字符串 ID。

## Alternatives considered

- **运行时反射调用客户端自身的解密方法** ——
  最强理由：完全绕过控制流混淆，结果 100% 准确，且实现极简
  （定位解密入口 → 遍历 ID 空间 → 逐条调用并记录）。
  采纳原因：解密器是静态方法、签名简单、可反射直接调用；
  实测一次跑通全部 7,806 条，无需理解任何混淆细节。

- **放弃字符串还原，只靠动态调试按需查看** ——
  最强理由：零前期投入。
  否决原因：本案例需要大规模检索（找授权相关方法名、资源键、注册表键），
  按需调试无法支撑全文检索式分析。

## Consequences

- 该路线被否定的直接原因是：解密器本身被施加了重度控制流混淆
  （大量 `if (0 == 0) {}` 死代码与 `_ = N; if (M == 0) {}` 噪声），
  静态还原需要先做控制流去平坦化，成本远高于反射调用。
- **可复用的判据**：当"被加密的数据"其解密器**仍是可调用的托管方法**时，
  优先走运行时反射转储，不要静态还原解密器。
- **已知上限**：反射方案要求解密器可被反射调用（非 Native、无强依赖）；
  若解密器位于 Native 层或依赖启动期状态，此路不通，需回到静态路线。
