# Agent Note: 全局改写通用空值检查助手

Status: rejected — 该助手在全程序有 100+ 处调用，全局改写会破坏无关功能

## Problem

授权装载状态机中唯一的判定点调用了某个"字符串是否为空/无效"的助手方法。
最省事的做法是直接让该助手恒返回期望值。

## Proposal

改写该助手方法体（使其恒返回 `true`），一次性绕过授权校验。
优点：只需改一个方法，不必逐个定位调用点。

## Alternatives considered

- **只改写调用点，不动助手本身** ——
  最强理由：助手方法在全程序有 100+ 处调用，语义是通用的
  "字符串是否为空"；只改授权流程中的**那一个调用点**，
  作用域精确，不影响其它逻辑。
  采纳原因：实测全局改写会导致配置文件解析异常，
  **设置项被清空**；而单点改写后 EULA、设置存储等全部正常。

- **在授权流程外层拦截，不碰任何 IL** ——
  最强理由：零侵入。
  否决原因：授权流程是编译进状态机的，外层无可插入的托管钩子；
  且该路线无法证明"二进制级改写可行"这一核心论点。

## Consequences

- **可复用的判据**：改写任何方法前，先统计该方法的**全程序调用点数量**。
  调用点越多、语义越通用（"空值检查""类型转换""日志"这类工具方法），
  越不能全局改写 —— 副作用会扩散到无关功能。
- **代价**：单点改写需要先精确定位授权流程中的那一处调用
  （在加密代码节区解密后按调用指令模式匹配），前期定位成本更高，
  但产出可控。
- **必须保留的纪律**：改写后要验证**无关功能仍正常**
  （本案例的验收点是 EULA 与设置项未被清空）。
