# Agent Note: 同进程内批量验证多个变体

Status: rejected — 程序集标识相同，同进程加载会返回已加载实例导致结果误判

## Problem

一次生成多个补丁变体后，需要逐个验证授权态是否被翻转。
最省事的做法是在**一个探针进程里循环加载所有变体**，逐个调用判定方法。

## Proposal

写一个探针程序，在同一进程内对每个变体文件依次执行 `Assembly.LoadFrom`，
调用授权态查询方法并打印结果。

## Alternatives considered

- **每个样本启动一个独立探针进程** ——
  最强理由：绕开程序集标识冲突。
  采纳原因：实测同进程方案下，**所有变体都返回同一个结果**，
  与预期（部分 True、部分 False）不符 —— 这正是标识冲突的典型症状。

- **用不同的 ApplicationDomain 隔离加载** ——
  最强理由：同进程内即可隔离，启动开销小。
  否决原因：被测程序集内部有跨域的静态状态与反射调用，
  分域加载会引入新的失败模式，调试成本高于"直接多起一个进程"。

## Consequences

- **根因**：所有变体都是从同一个原版样本补丁而来，
  其**程序集标识完全相同**（同名、同版本、同公钥令牌）。
  运行时对已加载的程序集按标识去重，第二次 `LoadFrom` 返回的是**第一次加载的实例**。
- **可复用的判据**：只要"多个待验证文件共享程序集标识"，就必须进程级隔离。
  这与文件路径、文件名、是否复制到不同目录**无关**。
- **代价**：验证耗时增加（每次进程启动 + 程序集加载）；
  作为交换，结果可信。此项已写入交付文档的硬性注意事项。
- **附带发现（同一主题下的另一处踩坑）**：为便于无 UAC 环境自动化测试，
  曾尝试把应用清单中的提权要求改为 `asInvoker`。
  实测结果是**进程存活但不创建主窗口**（应用会自提权重启）。
  因此**必须保留原始提权清单**，该开关只能用于明确知晓后果的自动化场景。
