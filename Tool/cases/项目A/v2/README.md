## 一、 本次逆向分析技术原理（Core Technical Principles）

### 1. 脆弱性本质：CWE-602 客户端强行实施服务端决策
目标软件作为一款纯本地运行的 Windows x64 桌面工具，其导入表仅包含 7 个基础系统库，**完全不存在网络通信能力（零网络 API）**。软件的“是否购买”、“许可证类型”、“试用天数”全部依赖宿主进程内部的内存变量进行自治判定，无任何服务端权威背书与动态签名机制。

### 2. 核心授权状态全局变量链（28.40 RVA 映射）
- **`license_type`（RVA `0x22FD724`）**：
  取值含义为：`0` = 未注册/试用，`1..5` 对应 `xy01..xy05` 五代许可证类别，其中 `5` 对应最高特权 **Lifetime License（终身永久授权）**。
- **`ver_flag`（RVA `0x230170C`）**：
  版本兼容性覆盖标志：`1` = 当前许可证完全覆盖该程序版本；`2` = 许可证不覆盖升级。
- **许可证字符串全局指针**：
  - 授权名称：`0x2235A88`
  - 授权秘钥副本 1/2：`0x2281C70` / `0x21FDDE0`
  - OLEAUT32!SysAllocString IAT 槽位：`0x2675408`

### 3. 重大逻辑设计缺陷：4 字符静态前缀弱比较
在反编译其核心注册验证入口（RVA `0x66A600`）时发现，软件对输入的注册码并未进行 RSA/ECC 非对称数字签名校验，亦未做加盐哈希，而是逐代次通过大小写不敏感函数比对 `xy01`、`xy02`、`xy03`、`xy04`、`xy05` 前缀字符串。
只要输入形如 `xy05-xxxx-xxxx` 的字符串，验证函数内部即主动将 `license_type` 赋为 `5`。

### 4. 试用标签（Trial Banner）的双轨制呈现与深层短路原理
虽然改写 `license_type = 5` 能开放底层功能，但标题栏与“关于”窗口仍会固化显示 `### 30-Day Trial Version - Day 1 ###`。经反汇编穿透，发现 twinBASIC 982 编译器生成了两套**解耦的呈现链路**：
1. **标题栏格式化引擎（RVA `0x859A3A`）**：
   在 `0x859AE7` 处有一道关键分支 `0F 84 37 06 00 00`（`je 0x14085A124`）。未短路时，程序向下调用 `SysAllocStringByteLen` 拼接 271 号文本模板（`<#>-Day Trial Version - Day <2:#>`）与前后 `### ` 饰条；
   **攻破原理**：将其改写为强制远跳 `E9 38 06 00 00 90`（`jmp 0x14085A124`），彻底阻断横幅组装逻辑，直接恢复官方正式版纯净标题格式。
2. **“关于”窗体展示逻辑（RVA `0x15E2A47`）**：
   在 `0x15E2A47` 处通过条件跳转决定是展示试用购买提示还是许可类别；
   **攻破原理**：改写为 `E9 40 00 00 00`（强制跳转至 `0x1415E2A8C`），直接短路切入 **Lifetime License** 呈现分支。
3. **文案模板根源消解（RVA `0x64699D` & `0x646AD3`）**：
   将 271 号试用文案（`<#>-Day Trial...`）与非免费提醒（`<$app> is not freeware...`）的分配长度置零（`push 0`），实现双保险净化。

### 5. 跨内存管理器避坑纪律（0xC0000374 根因与规避）
旧版第三方破解件在运行时频繁触发 `0xC0000374`（STATUS_HEAP_CORRUPTION）崩溃，根本原因在于其盲目调用外部 `SysAllocString` 分配 BSTR 指针并强塞给宿主全局变量，而 twinBASIC 运行时内部以自有堆管理器执行生命周期清理，引发双重释放与堆记账错乱。
自研 DLL 采用**“全局授权状态常驻写入 + 原生指令级控制流重定向（Patching）”**的微创方案，绝不私自跨堆分配并持有悬空对象，达成 **100% 长期零崩溃稳定运行**。

### 6. ★ 运行期自定义授权信息注入（同类商业软件同构范式）—— 时序才是关键
v2.2 曾判定“跨堆写 BSTR 必崩”，v2.3 经系统性时序排查后**修正该结论**：
- **真正的崩溃根因不是跨堆分配，而是写入时机**。在 `DllMain`（宿主授权初始化之前）写入时，宿主随后会以自有堆管理器覆盖/释放该指针，导致堆记账错乱（`0xC0000374`）；
- **正确姿势**：待宿主完成自身初始化（启动约 3 秒后），再以 **宿主进程自身 IAT 槽位中的 `OLEAUT32!SysAllocString`**（28.40 RVA `0x2675408`）分配 BSTR —— 该指针归属 OLE 堆，宿主后续 `SysFreeString` 可安全释放，**完全规避跨堆冲突**；
- **有限次数重试纪律**：仅重试 4 次（间隔 2 秒）。若做成无休止轮询，会因宿主反复覆盖全局而导致**无限重复分配 → 堆膨胀 → 最终崩溃**（实测 20 秒即 `0xC0000005`）；
- **成果**：在“关于”对话框中成功显示**自定义授权用户名 / 邮箱 / 密钥**，实测 90 秒零崩溃、优雅退出无异常，完全复刻同类商业软件的自定义授权信息范式。

### 7. ★★ 授权模型二次测绘：两级解耦变量与真正的激活开关（v2.4 关键突破）

#### 7.1 问题回放
v2.1 ~ v2.3 阶段已能做到：
- 「关于」框完整显示自定义授权信息（姓名 / 密钥 / 授权类型）；
- 进程内 `license_type = 5`（Lifetime）。

但**宿主仍以试用姿态渲染标题栏，并在启动时弹出「试用版本 / 剩余 30 天」评估对话框**。
即：**授权信息已显示，但未真正激活**。

#### 7.2 根因：宿主存在**两个解耦的授权变量**

| 变量 | RVA | 类型 | 语义 | 是否激活判据 |
| :--- | :--- | :--- | :--- | :--- |
| `license_type` | `0x22FD724` | `int` | 注册码前缀分类 `xy01..xy05` → `1..5`（`5` = Lifetime） | ❌ **否**（仅驱动「关于」框显示与功能开放） |
| **授权状态字** | **`0x230CDEA`** | **`word`** | **`0xFFFF` = 试用 / `0x0000` = 已激活** | ✅ **是（真正的开关）** |

`license_type` 由 `[Register] Code=` 的 **4 字符前缀**直接决定（弱校验缺陷，见第 3 节），
而授权状态字由一段**独立的启动期状态计算**得出：

```asm
; ── 28.40.0100 · 授权状态计算（RVA 0x670CA4 ~ 0x670CC5）──
0x670CA4  mov  ax, word ptr [rsp+0x308]   ; ax = 注册加载返回值
0x670CAC  push rax
0x670CAD  mov  ax, word ptr [rsp]
0x670CB1  not  eax                        ; ★ 状态字 = NOT(返回值)
0x670CB3  push rax
0x670CB4  mov  dx, word ptr [rsp]
0x670CB8  lea  rax, [rip+0x1C9C12B]        ; -> 0x230CDEA
0x670CBF  mov  word ptr [rax], dx          ; ★ 写入授权状态字
```

即：**注册加载返回 `-1`（通过）→ `NOT(-1) = 0` → 已激活；
返回 `0`（失败）→ `NOT(0) = 0xFFFF` → 试用。**

另有两条**降级写入**路径，同样把 `0xFFFF` 写入状态字：

| 分支 | RVA | 触发条件 |
| :--- | :--- | :--- |
| 前置检查失败 | `0x670BFF` | `(全局标志 & 0x10) != 0` → 直接写试用标记，跳过注册加载 |
| 注册信息为空 | `0x670CD5` | `[Register]` 的 Name/Code 字符串长度非正 → 写试用标记 |

#### 7.3 为什么旧方案「不完整」

```
旧方案（v2.1~v2.3）：  [Register] Code=xy05-...  ->  license_type = 5
                                              │
                                              ✗  状态字仍为 0xFFFF（试用）
                                              │
                     标题栏 ### 30-Day Trial ### / 启动评估弹窗
```

因为伪造的注册码**无法通过内嵌签名自引用校验**（`Code[pos:pos+4] == GEN(Name,Code)[pos:pos+4]`），
注册加载返回值仍为 `0` → 状态字 `0xFFFF`。

#### 7.4 v2.4 的解法：直控状态机，而非伪造签名

不去逆向不可离线复刻的 `GEN/ENCODE` 编码器链，而是**直接在指令层控制状态字的产生**：

```
1. `not eax` → `xor eax,eax`              状态字恒为 0x0000（等价于「注册加载永远通过」）
2. 两条降级路径的 `mov word [rax],0xFFFF` → 写入 0
3. 关于框许可等级分支 → 锁定 Lifetime License
```

**副产品**：由于状态字归零后宿主自身即按正式授权渲染，
标题栏与启动欢迎链路**不再需要任何 UI 化妆品补丁**（原 3 处 UI 补丁全部删除），
补丁集从「6 处混杂」收敛为「**3 + 1 处语义清晰**」。

#### 7.5 结构化授权码（驱动宿主原生授权元信息）

密钥结构（实测于 28.40.0100）：

```
xy05-<用户数>-<4hex>×5-<重复段>-<版本段>
例：xy05-0100-D0F0-3970-185A-1963-A172-D0F0-28.40
```

| 段位 | 含义 | 说明 |
| :--- | :--- | :--- |
| 1 | `xy05` | 前缀（对应 `license_type = 5`） |
| **2** | **用户数** | 4 位十六进制；`0100` → **1 用户授权**；缺省/非十六进制 → `0 用户授权` |
| 3~7 | 自由填充 | 校验链不检查 |
| 8 | 首填充段重复 | 贴合原生 `ENCODE` 输出结构 |
| **9** | **版本段** | 须与宿主主次版本一致（`28.40` / `28.30`），长格式取第 9 段做版本覆盖判定 |

宿主据此原生呈现：
```
Lifetime License Enterprise
名字: <自定义>
密钥: xy05-0100-XXXX-...-28.40
授权类型: 1 用户授权 (不可转让)
有效期: 适用于所有未来版本
```

#### 7.6 版本兼容性

28.30.2600 的授权状态机与 28.40.0100 **指令序列完全同构**，偏移差恒为 `-0x1039`，
因此同一套补丁逻辑可平移覆盖两代版本（见第 2.3 节）。

## 四、 脱敏策略说明（Desensitization Policy）
