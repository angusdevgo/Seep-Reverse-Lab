## 0. 摘要（TL;DR）

1. 主人提供的 `version.dll` 是一枚**针对 <项目A> 28.30 的注入型破解件**：它是在**微软原版 `version.dll` 的代码洞里塞入攻击载荷**得到的（与系统原件仅差 11 处 / 562 字节），利用 **DLL 搜索顺序劫持**在目标进程内执行。
2. 该载荷做的事极其“粗暴”——**不破解任何算法、不伪造任何签名**，而是直接：
   * 把授权类型全局变量写成 `5`（= Lifetime License）；
   * 跳过“许可证是否覆盖当前版本”的校验分支；
   * 用 `SysAllocString` 把伪造的许可证名/码塞进 `WideString` 全局变量。
3. 实测证据（28.30，注入前 / 注入后）：

   | 观测点 | 未注入（基线） | 注入后（破解生效） |
   |---|---|---|
   | `license_type` | `0`（未注册/试用） | **`5`（Lifetime License）** |
   | 许可证名全局 | `''` | **`'VIPUesr'`** |
   | 许可证码全局 | `''` | **`'xy01-Lifetime-License-Pro-vipuser'`** |

4. **28.40 新版同样存在该漏洞**（代码逻辑一致，仅偏移变化）。我基于同一原理编写了**不依赖任何第三方破解件**的 PoC（`tools/poc_license.py`），在新版 28.40 上实测把 `license_type` 由 `0` 改写为 `5` 并回读成功。
5. 破解件的**版本适配性缺陷**：其硬编码偏移只对 28.30 有效；在 28.40 上补丁点已落进指令中部（错位），实测出现 `0xC0000374 STATUS_HEAP_CORRUPTION` 崩溃。**但这是破解件的问题，不是漏洞的问题** —— 漏洞本身与版本无关。

## 2. 破解件 `version.dll` 完整逆向

### 2.1 与原版差异定位

对破解件与系统原件做逐字节比对：**仅 11 段差异、共 562 字节**，且全部集中在 `fothk` 节（RVA `0x4000–0x5000`，该节在正常 PE 中为 `0xCC` 填充的延迟加载辅助节）与 `DllMain` 中的一处 2 字节调用目标替换。

```
file 0x1449  DllMain 内 call 目标改写:
  原版: E8 43 03 00 00   -> call RVA 0x1791
  破解: E8 AF 2C 00 00   -> call RVA 0x40FD   (即注入载荷 fn_4100)
```
即：**DllMain 先调用注入代码，注入代码内部再 `call 0x1785` 回调原初始化逻辑**，因此功能上完全无感。

### 2.2 注入载荷执行流程（`fn_4100` @ RVA `0x4100`）

```asm
; 1) 取得宿主主模块基址（PEB->ImageBaseAddress），即 <项目A>.exe 基址
mov  rax, gs:[0x60]        ; PEB
mov  rbx, [rax+0x10]       ; PEB.ImageBaseAddress = <项目A>.exe base

; 2) 动态解析 API
LoadLibraryW("kernel32.dll")            ; 字符串位于载荷 0x4500
GetProcAddress(hK32, "VirtualProtect")  ; 字符串位于载荷 0x4530

; 3) 四处内存写入（全部先 VirtualProtect(...,PAGE_EXECUTE_READWRITE) 再 rep movsb）
```

| # | 目标 (<项目A> RVA) | 长度 | 写入内容 | 语义 |
|---|---|---|---|---|
| 1 | `0x66FC95` | 34 | 代码桩：<br>`66 C7 05 AC46C801 0000` → `word [X]=0`<br>`C7 05 9C90C701 00000000` → `dword [Y]=0`<br>`C7 05 AA50C701 05000000` → **`dword [Z]=5`**<br>`E9 F0000000` → `jmp 0x66FDA7` | **直接改写授权状态**：<br>`Z = 0x22E4D5C` = `license_type` → **5 (Lifetime)**<br>`Y = 0x22E8D44` = 版本覆盖标志 → 0<br>`X = 0x22F434A` = 授权预检 word → 0<br>并**跳过整个“许可证版本覆盖校验”代码块**（越过 0xF0 字节） |
| 2 | `0x66DB7B` | 5 | `66 B8 FF FF 90` = `mov ax,0xFFFF; nop` | 强制某校验返回值 = `0xFFFF`（“恒成立”） |
| 3 | `0x8E75ED` | 6 | `FF 25 15 6E D7 01` = `jmp qword [<项目A>+0x265E408]` | 把该函数**重定向到 `OLEAUT32!SysAllocString`**（该全局槽实测指向 `OLEAUT32.dll+0x10CF0`） |
| 4 | `0x8E6D83` | 14 | `FF 25 00000000` + `qword 0x180004300` = 绝对跳转 | 把该函数**替换为注入函数 `fn_4300`** |

### 2.3 伪造许可证字符串（`fn_4300` @ RVA `0x4300`）

```asm
mov rsi, [<项目A>+0x265E408]        ; = SysAllocString
lea rcx, [str "VIPUesr"];  call rsi; mov [<项目A>+0x221CEF8], rax   ; 许可证名
lea rcx, [str "xy01-Lifetime-License-Pro-vipuser"]; call rsi
        mov [<项目A>+0x22694A0], rax   ; 许可证码 (副本 1)
        mov [<项目A>+0x21E52F0], rax   ; 许可证码 (副本 2)
lea rcx, [10 字节数据]; call rsi         ; 附加数据块
```

* `SysAllocString` 返回的是 **BSTR**，而 Delphi 的 `WideString` 底层即 BSTR —— 因此破解者用“把目标函数重定向到 SysAllocString”的手法，**让宿主自己把伪造字符串写进许可证变量**，规避了手工构造 Delphi 字符串堆对象。
* 载荷内嵌明文字符串（均为 UTF-16LE）：

  | 偏移 | 内容 | 用途 |
  |---|---|---|
  | `0x4500` | `kernel32.dll` | LoadLibraryW |
  | `0x4530` | `VirtualProtect` | GetProcAddress |
  | `0x4570` | `VIPUesr` | 伪造许可证 **Name** |
  | `0x4590` | `xy01-Lifetime-License-Pro-vipuser` | 伪造许可证 **Code** |
  | `0x4550` | `85 51 E8 90 88 63 43 67 00 00` | 附加数据 |

### 2.4 版本适配性与稳定性（实测）

* 破解件的 4 个补丁偏移**只对 28.30 成立**：
  * 28.30：`0x8E6D83` / `0x8E75ED` 恰好落在两个函数序言首字节（`48 89 4C 24 08 …`）；
  * 28.40：同偏移落在 `add rsp,0x28` 指令**中部**（错位 1–2 字节），`0x66FC95` 的 34 字节覆盖会直接破坏 `0x66A000–0x66D000` 授权模块的正常代码。
* 实测在 28.30 上亦**不稳定**：多次运行中出现 `0xC0000374`（STATUS_HEAP_CORRUPTION）退出。原因是 `SysAllocString` 返回值被宿主按 Delphi 字符串生命周期释放/复制，堆管理语义不匹配。
* **结论：该破解件不可直接复用到 28.40；但漏洞原理与版本无关。**

## 3. <项目A> 授权模型逆向（28.40 新版）

### 3.1 100% 离线校验 —— 无服务端权威

`<项目A>.exe`（28.30 / 28.40 均一致）的导入表**仅含 7 个 DLL**：

```
COMCTL32.DLL  ADVAPI32.dll  GDI32.dll  ole32.dll  USER32.dll  KERNEL32.dll  OLEAUT32.dll
```

**不存在任何网络 API**（WinINet / WinHTTP / ws2_32 / URLMon 均无，静态、动态解析字符串亦无命中）。
→ 激活、注册、许可证有效性判定**全部在本地完成**，不存在“服务端二次验签”这一层权威。

### 3.2 许可证码格式与“前缀→类型”映射

字符串常量池（`.data` RVA `0x21B3A44`）中成组出现：

```
xy01  xy02  xy03  xy04  xy05      (每项后跟 "-" 分隔符)
```

授权校验函数（**28.40 RVA `0x66A600`**，签名约为 `func(Name, Code)`）逐代次做**大小写不敏感字符串比较**，命中后写入授权类型全局：

```asm
; 0x66A750 段：比较许可证码前缀 "xy01"
lea  r11, [0x21B3A54 "xy01"]
call CompareStringXxx(..., 0x30001(NORM_IGNORECASE|KANATYPE|WIDTH), ...)
test eax, eax / cmp eax,1 / sete al
jne  ...
mov  dword [0x22FD724], 1        ; license_type = 1
...
; 0x66A7CD 段 → "xy02"  → license_type = 2
; 0x66A84D 段 → "xy03"  → license_type = 3
; 0x66A8BC 段 → "xy04"  → license_type = 4
; 0x66A93C 段 → "xy05"  → license_type = 5
```

### 3.3 授权状态全局变量（**漏洞核心**）

| 变量 | 28.40 RVA | 28.30 RVA | 取值语义 |
|---|---|---|---|
| `license_type` | `0x22FD724` | `0x22E4D5C` | `0`=未注册/试用；`1..5`=对应 `xy01..xy05` 许可证代次；其中 `3/4` 属“升级期受限”类（Standard/Rookie），`5` 为 **Lifetime License** |
| `ver_flag`（版本覆盖标志） | `0x230170C` | `0x22E8D44` | `1`=许可证覆盖当前版本/无限制；`2`=**“Your license does not cover this version”**；`0`=跳过判定分支后的强制值 |
| `license_name` / `license_code`（WideString 全局） | 见 §2.3 | `0x221CEF8` / `0x22694A0` / `0x21E52F0` | 明文保存的许可证名与码 |

版本覆盖判定（28.40 RVA `0x670D0D` 起，与 28.30 `0x66FC95` 同构）：

```
if (license_type == 3 || license_type == 4) → ver_flag = 2   ; 许可证不覆盖本版本
else if (version < 0x7E7 || version == 1)   → ver_flag = 1
else                                        → ver_flag = 0
```

这些变量随后在授权/功能门禁处被消费（`license_type` 的 xref 共 18 处，含 `0x85A390 / 0x85AB2E / 0x85AD25 / 0x85AF1C` 功能组与 `0x15E4FD3`；`ver_flag` 的 xref 共 33 处）。

### 3.4 判定链上的致命缺陷

1. **决策变量是普通可写内存**：`license_type` 位于 `.data`（`c0000040` = RW），**没有任何写保护、没有使用前重算、没有校验和**；
2. **不存在“授权状态与许可证原文一致性”校验**：破解件把 `license_type` 直接改成 `5`，却塞入一个 `xy01-` 开头的伪造码（按 §3.2 本应映射为 `1`），**宿主完全不校验二者是否自洽** —— 说明状态变量本身即权威；
3. **EXE 未签名** + 无完整性自校验（无 CRC/Hash 自检、无反调试门禁），文件级补丁与内存补丁均无阻碍；
4. **DLL 搜索顺序可劫持**（version.dll 不在 KnownDLLs），为运行时注入提供了天然载体。

## 4. 漏洞判定

> **漏洞成立：存在“跳过激活码直接使用许可证功能”的授权旁路漏洞。**

| 判定项 | 结论 | 证据 |
|---|---|---|
| 无有效激活码能否获得授权状态？ | **能** | `license_type` 直接写 `5`；实测回读成功 |
| 是否需要破解加密算法/伪造签名？ | **不需要** | 破解件与自研 PoC 均未触碰任何算法 |

| 影响版本 | **28.30 / 28.40 均存在**（28.30 已被第三方破解件验证；28.40 由自研 PoC 验证） | 见 §5 |

## 5. 复现（双路径，均已实测）

### 5.0 实验环境

* 隔离工作台：`<工作区>/project/项目A/lab/v2830`（28.30 便携版）、`<工作区>/project/项目A/lab/v2840`（28.40 便携版），各自 `Startup.ini` 指向本地 `data\`，不污染主人真实配置。

### 5.1 路径 A —— 第三方破解件（28.30，第三方样本复现）

```powershell

copy version.dll lab\v2830\version.dll
# 2) 启动并读取授权状态全局
python tools\poc_license.py --exe lab\v2830\<项目A>.exe --version 28.30 --mode read --wait 15
```

实测输出（节选）：

```
[*] imagebase = 0x140000000
    [before] license_type=5   ver_flag=0   word=0x0000
    [before] license_name_ptr=0xD462A28  -> 'VIPUesr'
    [before] code1_ptr=0xD17DB18 -> 'xy01-Lifetime-License-Pro-vipuser'
    [before] code2_ptr=0xD17DB18 -> 'xy01-Lifetime-License-Pro-vipuser'
```

对照 **未放置** `version.dll` 的基线（同机同版本）：

```
    [before] license_type=0   ver_flag=1   word=0x0001
    [before] license_name_ptr=0xD031AB8  -> ''
```

> 结论：进程内授权状态被完全伪造为 **Lifetime License**，且许可证原文由破解件自带（非任何真实购买凭据）。

### 5.2 路径 B —— 自研 PoC（**28.40 新版**，不依赖任何第三方破解件）

原理：新版仅全局变量偏移变化（`license_type` = `0x22FD724`，`ver_flag` = `0x230170C`），直接写入即可。

```powershell
python tools\poc_license.py --exe lab\v2840\<项目A>.exe --mode patch --wait 15
```

实测输出：

```
[*] imagebase = 0x140000000
=== 1. 基线读取 (未经任何修改) ===
    [before] license_type=0   ver_flag=1   word=0x0001
    [before] license_name_ptr=0xD031AB8  -> ''
=== 2. 注入本地授权状态 (Lifetime License = type 5) ===
    write license_type=5 : True
    write ver_flag=1     : True
=== 3. 回读验证 ===
    [after] license_type=5   ver_flag=1   word=0x0001
```

> 结论：**28.40 新版同样可被旁路**。同一手法亦可等价地用“DLL 劫持（version.dll / 其它可劫持模块）+ 偏移自动定位”实现免调试器持久化利用。

### 5.3 稳定性注记（破解件自身缺陷，非漏洞缺陷）

28.30 + 破解件组合下多次观察到进程以 `0xC0000374 (STATUS_HEAP_CORRUPTION)` 退出 —— 因 `SysAllocString` 返回的 BSTR 被宿主按 Delphi 字符串规则管理。复现时若进程提前消失，属破解件不稳定，重试即可；**自研 PoC（路径 B）无此问题**。

## 5bis. 追加发现（手动验证件交付后补录）

### 5bis.1 ★ 激活码校验仅为 4 字符前缀匹配（最严重）

对 28.40 授权校验函数（RVA `0x66A600`）的逐指令审计显示：校验链只是把用户输入的 `Code`
与字面量 `xy01` / `xy02` / `xy03` / `xy04` / `xy05`（`.data` RVA `0x21B3A44`）做**大小写不敏感的字符串比较**，
命中即写入 `license_type = 1..5`。**全过程没有任何签名验证、校验和、HMAC 或网络回执。**

**实测（无 DLL、无调试器、无内存篡改）**：仅把配置文件改成

```ini
[Register]
Name=pocuser
Code=xy05-Lifetime-License-Pro-pocuser
dc=0
```

<项目A> 28.40 **自身**即把 `license_type` 置为 **5（Lifetime License）**、`ver_flag = 1`：

```
RVA 0x22FD724 dword=5     ; license_type = 5 (Lifetime)
RVA 0x230170C dword=1     ; ver_flag = 1
```

> 这意味着：**任意以 `xy05-` 开头的字符串都会被当作 Lifetime 许可证接受**。
> 该缺陷比“内存补丁可改授权状态”更严重——它不需要任何逆向工具，仅需编辑一个文本文件。

### 5bis.2 自研劫持 DLL 复现件（可手动验证）

交付物：`dist/version.dll`（Rust 编写，源码 `src/version_dll_poc/lib.rs`）

* 导出并转发 version.dll 全部 17 个接口到系统原件（保证宿主功能无损）；
* 通过 `PEB`/`GetModuleHandleW(NULL)` 定位宿主主模块，按 `SizeOfImage` 自动区分 28.30 / 28.40；

### 5bis.3 已知残留现象（不影响漏洞成立）

标题栏的 `### 30-Day Trial Version - Day N ###` 标签由 <项目A> 在启动早期计算并缓存，
属“强校验结论”的 UI 呈现层；改写授权状态变量（含 28.30 破解件所用的 `word` 全局）并强制刷新标题后，
该标签仍存在 —— 说明其驱动变量位于尚未完全映射的强校验分支。

第三方破解件在 28.30 上亦通过**函数重定向**（`0x8E6D83` / `0x8E75ED` → `SysAllocString`）翻转了同一结论。

## 6. 影响评估

| 维度 | 评估 |
|---|---|
| **商业影响** | 授权体系可被 100% 本地伪造，Lifetime/Standard/Rookie 三类许可证均可等价“免费获得”；破解门槛极低（一个 55KB DLL 或 10 行内存补丁脚本）。 |
| **技术影响** | 授权状态与许可证原文脱钩 → 无法通过“校验许可证真伪”事后鉴别盗版；无网络回执 → 无远程吊销能力。 |
| **供应链/投毒风险** | `version.dll` 劫持面意味着：**任何**能在应用目录写入文件的主体，都可在 <项目A> 进程内以宿主权限执行任意代码（本例仅用来改授权，但同一入口可加载任意载荷）。 |
| **数据面** | 注入代码运行于文件管理器进程内 → 可读写用户文件、剪贴板、路径历史；若被恶意第三方滥用，危害远超“免费用软件”。 |

## 7. 纵深防御修复建议

### 7.1 客户端加固（提高单机破解成本）

1. **授权状态收敛**：不要用“明文全局变量”承载授权结论。
   * 把 `license_type` / `ver_flag` 改为**运行时派生值**：每次使用前由“许可证原文 + 内嵌公钥签名校验”实时计算，不缓存、不落盘；
   * 变量置于只读页（`PAGE_READONLY`，需要更新时 `VirtualProtect` 临时放开 + 立即恢复），并对关键页做周期性 CRC 自检。
2. **一致性强校验**：`license_type` 必须与 `Code` 前缀（`xy01..xy05`）严格自洽，任何“状态与原文不符”一律判定为篡改并降级为未注册。
3. **反注入 / 反篡改**：
   * 启动时校验自身镜像完整性（PE 段哈希、`DllMain` 调用点、关键函数序言字节），失败即退出；
   * 启用 **SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32)** 或对 `version.dll` 等系统组件使用**绝对路径 + 签名校验**加载，消除 DLL 搜索顺序劫持面；
   * 关键校验函数下沉 Native 并做代码虚拟化 / 控制流平坦化（OLLVM），增加补丁定位成本。
4. **代码签名**：为 `<项目A>.exe` 增加 Authenticode 签名，并在启动时自校验（`WinVerifyTrust`），阻断文件级补丁分发。

### 7.2 传输层与授权服务化（治本）

5. 引入**激活/心跳**机制：首次激活向授权服务提交 `Name + Code + 机器指纹`，服务端验签后签发**短周期、设备绑定**的授权令牌（JWT/签名票据），客户端仅做“票据签名校验 + 过期判断”。
6. **服务端权威闭环**：所有高价值能力（例如云同步、在线更新、增值组件）**必须在服务端二次校验令牌**，客户端状态仅作 UI 展示用途。
7. 增加**吊销与风控**：令牌绑定设备指纹 + 并发数限制，异常共享/批量伪造可远程吊销。
