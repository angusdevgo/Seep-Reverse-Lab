## 一、审计结论（TL;DR）

1. **付费权益完全由客户端判定（CWE-602）**：会员到期时间、会员类型、设备权益、试用状态、免广告资格全部从服务端以**明文整型字段**下发，客户端本地用单字节/单整型分支决定权益发放，没有可验证的签名令牌或服务端权威裁决。
2. **可利用性高**：在只读打开官方签名 EXE 的前提下，通过同目录 `winhttp.dll` 代理注入 + 运行时内存热补丁，即可把到期时间钉死为 `2099-12-31`、会员类型置 1、设备权益置 1、试用状态置 2、免广告信号强制发射。
3. **广告去除的根因不是"少画一个控件"，而是决策信号闸门可被短路**：客户端在 `Sub_140273D70` 内比较 `[rdx+4]` 后条件跳转，跳转目标决定是否发射 `member_remove_ad_ok` Qt 信号；把该 `je rel32` 填成 6 个 `NOP`，信号无条件发射，开屏广告与推荐横幅被 UI 层统一剥离。
4. **多进程会回写覆盖**：只改前台 UI 会被后台 `项目BNxService.exe` 的周期序列化冲刷。必须同时收敛 Service 的**解析、序列化、`is_valid_infos` 有效性门控**三处，才能做到断网/重启后权益不回退。
5. **版本更新会冲刷补丁**：新版更新器把 `is_upgradeable` 作为唯一判定；三端（Main / Service / Updater）同时把 `mov sil,1` 改为 `xor sil,sil`，即可让客户端自身得出"无更新"结论，避免被 CDN 差分包覆盖。
6. **与旧交付包的关系**：旧 v3 包（6.8.8.0 / 2026-10-23 构建）的 51 处点位在新构建上**命中率 0/51**。本次按语义锚点全量重标定为 54 处，并逐点核验通过。

## 三、漏洞原理

### 3.1 权威来源错位：服务端只下发"数据"，客户端负责"裁决"

正常设计应当是：服务端签发带签名与时效的权益令牌（JWT/HMAC/非对称签名），客户端只做**验签 + 展示**，且每次高价值操作都回到服务端二次裁决。

实际实现是：

```
服务端回包 JSON
  ├─ member_expired_at      (int64 时间戳)
  ├─ member_status          (int)
  ├─ member_type            (int)
  ├─ enabled_device_count   (int)
  ├─ member_trial_status    (int)
  └─ member_privilege_enable(int)
        │
        ▼
客户端 QJsonValue::toInt()/toVariant() 取值
        │
        ├─→ 写入账号对象 → UI 分支 (if member_type == 1) → 显示会员 / 去广告
        └─→ 序列化到本地缓存 nx_main.json → 下次启动继续信任
```

链路上**没有任何签名、MAC、时间戳绑定或服务端复核**。客户端只要在"取值"这一层把返回值换成常量，后续所有 UI、缓存、权限判断都会一致地认为用户是 VIP。这是 CWE-602 的教科书形态。

### 3.2 三层数据流：为什么只改一处会"闪回"

会员状态在三个位置被反复读写：

| 层 | 位置（新构建） | 作用 | 只改这一层的后果 |
|---|---|---|---|
| L1 网络回包反序列化 | `0x13B7EA0` 函数内 6 个取值调用 | 登录/刷新后写入内存账号对象 | 后台 Service 回写缓存后失效 |
| L2 本地缓存解析 A/B | `0x18BCAF0` / `0x18C0C80` | 启动时从 `nx_main.json` 还原 | 云端刷新后失效 |
| L3 本地缓存序列化 A/B | `0x18B7720` / `0x18C2970` | 把内存状态写回磁盘 | 重启后失效 |

三层的字段 key 是稳定的语义锚点：

- `member_expired_time` / `member_expired_at`（到期时间）
- `member_status` / `device_member_status`（会员/设备权益）
- `member_type`（会员类型，1 = VIP）
- `member_trail_status` / `member_trial_status`（试用状态）
- `enabled_device_count`（可用设备数）
- `member_privilege_enable`（免广告特权）

### 3.3 广告决策：短路"信号闸门"，而不是"返回值"

新构建的开屏广告/推荐横幅由 `sub_140273D70` 统一决策。关键指令：

```asm
0x140273DAF   cmp  byte ptr [rdx+4], r15b    ; r15b = 0，判断"是否已具备免广告资格"
0x140273DB3   0F 84 B9 01 00 00             ; je 0x140273F72 —— 不满足则跳过信号发射
0x140273DB9   48 8B B9 A8 01 00 00          ; mov rdi,[rcx+0x1A8]  (QObject)
0x140273DC3   48 8B 98 90 01 00 00          ; mov rbx,[rax+0x190]  (信号槽)
0x140273DCA   BA 13 00 00 00                ; mov edx,0x13         (参数个数)
0x140273DCF   48 8D 0D DA 30 D8 01          ; lea rcx,"member_remove_ad_ok"
0x140273DD6   FF 15 ...                     ; QString::fromAscii_helper
0x140273DF8   FF D3                         ; call rbx  —— 发射信号
```

早期做法是在函数入口写 `mov eax,1; ret`，这会连信号发射一起跳过（该函数不是纯 Getter，而是事件分发器），导致 UI 收不到"移除广告"的通知，广告仍会偶发出现。

正确做法是把 `0F 84 B9 01 00 00` 原地替换为 `90 90 90 90 90 90`：条件跳转消失，执行流**无条件穿透**到信号发射块。UI 的槽函数收到 `member_remove_ad_ok` 后，统一把开屏 WebView、侧边推荐栏、横幅容器置空/隐藏。

### 3.4 多进程状态竞争：`is_valid_infos` 是最后一道闸

`项目BNxService.exe` 是常驻服务，负责机器码绑定、许可证轮询、缓存落盘。它在两个通道解析账号信息（A/B），并在解析完成后检查 `is_valid_infos`：

- 解析通道 A：`0xE865C4` 调用 `is_valid_infos` 取值；
- 序列化通道 B：`0xE8C09B` 读取结构体 `[rbp+0x432]` 的字节写入 JSON。

如果 `is_valid_infos == false`，Service 会把本地档案当成"脏数据"回退到未授权默认值，并在下一次心跳时覆盖磁盘。只改 UI 不改 Service，就会出现"VIP 亮一下又掉"。

复现时同时做三件事：

1. 解析 A 的 `is_valid_infos` 取值调用 → `mov al,1; nop*3`；
2. 序列化的 `movzx ecx,[rbp+0x432]` → `mov cl,1; nop*6`；
3. 云端端点 `v1/member/trial` → 等长改 `v1/member/local`（避免服务端试用接口把状态刷回去）。

### 3.5 试用/购买引导流程

`AccountFlowManager::handleAccountFlowTransition`（新构建 `0x1378600`）根据 `member_type` 与试用状态决定弹"试用/购买/领会员"引导。关键分支：

```asm
0x141378B0B   cmp  qword [r14], 0
0x141378B0F   0F 8E ED 00 00 00   ; jle 0x141378C02 —— 跳过整个购买引导块
```

补丁 `E9 EE 00 00 00 90`（`jmp +0xEE; nop`）把条件跳转变成无条件跳转，目标地址与原 `jle` 完全一致（`0x1378C02`），因此不会破坏栈平衡或跳过初始化。

### 3.6 云控更新与远程推送

- **更新**：`is_upgradeable` 是纯客户端配置读取（`QJsonObject::value("is_upgradeable").toBool()`），三端都有同一段 `test al,al; je+5; mov sil,1; jmp+3`。把 `40 B6 01` 改成 `40 30 F6`（`xor sil,sil`），客户端永远认为"无新版本"，不会触发 CDN 差分包下载，也不会覆盖内存补丁。
- **远程**：`platform::isCurrentSessionRemoteSession()`（`0x18AFC0`）通过 `GetSystemMetrics(SM_REMOTESESSION)` + `GlassSessionId` 注册表判断远程会话；入口改 `33 C0 C3 90`（`xor eax,eax; ret`）恒返回 false。`Healthd` 守护进程拉起函数（`0xD3E60`）入口改 `C3` 直接返回。

## 四、重标定方法论（6.8.8.0 → 6.8.10.0）

新版不是重写，而是**按编译单元重排**。本次使用四类语义锚点，逐点推导而非猜平移量：

### 4.1 锚点类型

| 锚点 | 适用点位 | 定位方法 |
|---|---|---|
| 业务字符串（`member_remove_ad_ok`、`is_upgradeable`、`v1/member/trial`） | 广告闸门、更新判定、端点降级 | `.rdata` 字符串 → 扫描 `lea r/m,[rip+disp]` 求 xref |
| JSON 字段 key（`member_expired_time`、`device_member_status`、`is_valid_infos`） | 解析 A/B、序列化、`is_valid_infos` | `lea rdx,[rip+key]` 后固定 `+0x25` 处即取值调用；短 key 由 `movsd/movups` 内联构造，需反向解析 |
| 调用间距结构（`+0x94, +0x8C, +0x8B, +0x1AF, +0x2F2`） | 网络回包 6 连取值 | 枚举全部 `E8 rel32`，按间距序列匹配；再用"后 5 个 call 目标相同"二次过滤，全局唯一 |
| 栈偏移/指令字节（`[rbp+0x2C8]`、`[rbp+0x378]`、`40 B6 01`） | 序列化 A/B、`is_upgradeable` | 结构体布局未变，原字节可直接命中 |

### 4.2 关键判据

1. **同一函数内相对跳转位移不变**：`0F 84 B9 01 00 00`、`0F 8E ED 00 00 00` 在新版原样保留，可直接字节搜索。
2. **同一编译单元内字段间距不变**：序列化 A 的 5 个点间距 `+0x101 / +0xF1 / +0x1F0 / +0xD2` 与新构建 100% 吻合，用于互相印证。
3. **结构体栈偏移不变**：`[rbp+0x2C8]`、`[rbp+0x2D4]`、`[rbp+0x308]` 等在新构建完全一致，说明账号结构体未改布局。
4. **函数体规模指纹**：解析 A 与设备解析函数在新构建中仍为 `0x22AD` / `0x1519` 字节，与旧版一致，可直接用 `.pdata` 边界确认。

### 4.3 标定流程（可复现）

```
① 读 .pdata 建函数边界表（118,904 个函数）
② 全量扫描 lea/mov rip-relative，建 RVA → 目标字符串表（93,875 条）
③ 用业务 key 命中候选函数 → 在函数内按 +0x25 规则取调用点
④ 用调用间距/栈偏移/原字节三重校验
⑤ 逐点 memcmp 原始字节，0 偏差才写入 points_v4.json
```

## 七、点位总表（54 处）

> 坐标一律为 **RVA**，`VA = 0x140000000 + RVA`。
> `orig` 为磁盘原始字节（写入前强校验），`patch` 为运行时写入字节。

### 项目BNxMain.exe（前台 UI 主程序）—— 29 处

| # | RVA | 功能 | 原始字节 | 修补字节 | 点位 ID |

## 八、风险与影响

| 维度 | 说明 |
|---|---|
| **商业风险** | 本地即可解锁 VIP/去广告，厂商的订阅收入与广告曝光不再受客户端约束；仅靠客户端逻辑无法阻止。 |
| **完整性风险** | 权益状态可被本地缓存伪造并持久化；若服务端盲信客户端上报的 `member_type`/`device_member_status`，会造成**跨设备权益提升（BFLA）**。 |
| **攻击面** | 四个主进程均静态导入 `winhttp.dll`，且安装目录无该文件、该库不在 `KnownDLLs`，形成天然的 DLL 搜索顺序劫持面。 |
| **稳定性** | 补丁均为等长/等语义替换，且写入前做 PE 节区边界与原始字节双重校验；实测启动无崩溃、无闪退。 |
| **副作用** | `is_upgradeable` 恒假会同时关闭"检查更新"入口；若厂商强制服务端版本门槛，可能出现"必须升级才能登录"的提示。 |

## 九、修复建议（纵深防御）

### 9.1 架构级（根治 CWE-602）

1. **权益令牌化**：服务端签发带 `exp`、`device_id`、`features` 的短期 JWT（Ed25519/RS256），客户端只验签展示；到期时间不参与本地计算。
2. **服务端权威裁决**：所有特权动作（去广告素材下发、设备数提升、云手机开通）必须由服务端在**每次请求**时复核，不信任客户端上报的布尔/整型。
3. **广告物料服务端剥离**：无权益时服务端直接不下发广告素材 URL，客户端没有"本地开关"可改。

### 9.2 加载期（收敛劫持面）

4. `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32 | LOAD_LIBRARY_SEARCH_APPLICATION_DIR)`，并对应用目录内所有 DLL 做 Authenticode 链校验。
5. 把 `winhttp.dll` 等系统库加入应用级白名单校验（哈希/签名），发现同名伪造即拒绝启动。
6. 对 `nx_main` 目录做完整性清单（每个文件 SHA-256 签名），启动时校验。

### 9.3 运行期（提高热补丁成本）

7. `.text` 段周期性 CRC 抽检（重点覆盖决策函数），发现 `PAGE_EXECUTE_READWRITE` 或字节漂移即上报/退出。
8. 关键判定改为**多因子组合**（服务端签名 + 本地硬件指纹 + 时间戳），单点内存改写不足以通过。
9. 反调试/反注入：检测非官方模块加载、`CreateRemoteThread`、`VirtualProtect` 对 `.text` 的写操作。

### 9.4 编译期（提高逆向成本）

10. 对权益判定函数做控制流平坦化（OLLVM）/ 代码虚拟化（VMP），抹除明文字段名与信号名。
11. 字段名与端点字符串运行时解密，避免 `.rdata` 明文锚点。
12. 关键比较改为哈希/表驱动，避免单字节 `cmp/je` 可被 NOP。

### 10.2 设计要点（为什么是单文件 `winhttp.dll`）

- 四个宿主（Main/Service/RemoteService/Updater）**全部静态导入** `winhttp.dll`；
- 安装目录原本**没有** `winhttp.dll`，且该库**不在** `KnownDLLs`；
- 代理 DLL 用 88 个 `#[unsafe(naked)]` WinHttp 裸汇编桩（`mov rax,[rip+slot]; jmp rax`）动态转发到 `C:\Windows\System32\winhttp.dll`，**不需要** `_orig.dll`、`.def` 转发或改名；
- `DllMain` 只做纯内存初始化（`DisableThreadLibraryCalls` + 解析真实库 + `CreateThread`），所有 I/O 与打点在 worker 线程完成，避免加载器锁死锁；
- 每个点位写入前三重门禁：`rva_in_module` 节区边界 → `memcmp` 原始字节 → `VirtualProtect` 改属性；任一步失败只记录 `SKIP/MISMATCH`，不盲写。

### 10.3 已知限制

1. `项目BRemoteService.exe` 是 Windows 服务，需管理员权限 `sc stop` 后才会加载新 DLL；否则其 2 处点位不生效（不影响 VIP/广告）。
2. 若厂商再次重编译，`points_v4.json` 的 RVA 会失效；请用 `03_源码与工具` 中的锚点脚本按第四节方法论重标定。
3. 补丁只作用于**进程内存**，进程退出即消失；DLL 留在目录内会在下次启动自动重新打点，无需重复部署。
4. 本报告与工具仅用于已授权的沙盒审计与防御加固验证。
