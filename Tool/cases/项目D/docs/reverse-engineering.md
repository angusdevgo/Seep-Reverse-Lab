# 逆向过程记录（项目D · 授权校验链跨版本迁移）

> 目标：项目D 6.43 build 10 → build 11（6.43.11.2 / 6.43.11.3）
> 完整过程见工作区 case 目录（不随本仓库发布）；本文保留可复现的方法论与关键命令。

---

## 0. 问题背景：一次架构倒退

### 0.1 现象

用户反馈：执行「写入授权」后启动目标程序，弹出

```
System.ComponentModel.Win32Exception (0x80004005):
指定的可执行文件不是此操作系统平台的有效应用程序
```

调用栈指向 `Process.StartWithShellExecuteEx`，即 **PE 映像已被写坏**（Win32 错误 193 / `ERROR_BAD_EXE_FORMAT`）。

### 0.2 根因

第二代工具把补丁位点**硬编码为 build 10 专属的绝对文件偏移**，并**无条件把文件截断到 6,189,056 字节**：

```csharp
const int TARGET_FILE_SIZE = 6189056;      // build 10 专属常量
if (data.Length > TARGET_FILE_SIZE)        // 只看「比目标大」，完全不校验版本
    Array.Resize(ref data, TARGET_FILE_SIZE);
```

`6189056` 恰好等于 build 10 的节区表末尾（`0x5E7000`），被砍掉的 10,608 字节正是 Authenticode 签名 —— 对 build 10 是**正确的**。

但任何**体积更大的版本**走到这里，就会被拦腰砍断 `.rsrc` / `.reloc` 节区的原始数据 → PE 加载器直接拒绝。

### 0.3 架构演进对照

| 代 | 定位方式 | 跨版本 | 结果 |
|:--:|---|:--:|---|
| Gen 1 | **AOB 特征码搜索**（12 条） | ✅ | 可用 |
| Gen 2 | 硬编码绝对偏移（18 点 / 31 字节） | ❌ | **写坏映像** ← 本案例起点 |
| Gen 3 | 硬编码偏移 + PE 解析门禁 | ❌ | 不再写坏，但仍仅支持单版本 |
| **Gen 4** | **AOB 双态特征码**（14 条 / 3 版本验证） | ✅ | 本案例成果 |

> **核心教训**：Gen 2 为了「更精确」把特征码搜索降级成写死偏移，用一个隐含的版本假设换取了短期精确性。

## 1. 安装包拆解（自定义 SFX）

官方安装包是**自定义 SFX**：PE 本体仅 95,232 字节，其余 12,457,696 字节为 overlay。

### 1.1 条目格式（逆向确认）

```
[0x00] DWORD  原始大小 (uncompressed size)
[0x04] DWORD  压缩大小 (compressed size)
[0x08] FILETIME × 3
[0x20] zlib 流 (deflate, 78 DA)
```

链式排列：`next = cur + 0x20 + compressedSize`

### 1.2 提取

```python
pos = 0
while pos + 0x20 <= len(overlay):
    d0, d1 = struct.unpack_from('<II', overlay, pos)      # 原始/压缩大小
    data = zlib.decompress(overlay[pos + 0x20:])          # 解压载荷
    pos = pos + 0x20 + d1
```

**校验手段**：安装脚本（第一个条目）内含 `<P<n>="文件名">` 清单，与载荷顺序**逐条精确对齐** —— 用已知体积（`idman.chm` = 320,931、`idmantypeinfo.tlb` = 2,596）交叉验证映射正确。

结果：192 个条目全部解出，主程序位于**条目 #5**（压缩 2,602,327 → 解压 6,200,176 字节）。

> ⚠️ **踩坑**：安装包内是 **6.43.11.2**，而实际安装的是 **6.43.11.3**（体积相同、SHA256 不同）。必须**以真实安装文件为分析对象**，不能只信安装包。

## 2. 版本差异性质判定

### 2.1 相似度矩阵（按节区，相同偏移逐字节比对）

| 节区 | build 10 vs build 11 |
|---|---|
| `.rsrc` | **100.00%** 相同 |
| `.data` | **95.43%** 相同 |
| `.rdata` | 38.33% 相同 |
| `.reloc` | 35.45% 相同 |
| `.text` | **5.78%** 相同 |

`.text` 仅 5.78% 看似「重写」，但：

```
build 10  @0x400: 8B 44 24 04 83 F8 50 77 13 ... E9 F3 F9 20 00 E9 26 FA 20 00 C3
build 11  @0x400: 8B 44 24 04 83 F8 50 77 13 ... E9 03 FC 20 00 E9 36 FC 20 00 C3
                                                   └─ 仅 E9 rel32 目标不同 ─┘
```

跳转目标差 `+0x210` = `.text` VSize 增长量 ⇒ **代码整体位移，而非重写**。

### 2.2 位移曲线

以 64 字节窗口、4KB 步长，在 `±0x8000` 范围内搜索最佳匹配：

```
b10 RVA     位移      说明
0x400       +0        节区起点对齐
0x2400      +64       首次插入
0xD400      −608      删除
0x10400     −880      稳定区间
0x21400     −608
0x2F400     −144      大幅插入后回落
0x34400     −368
0x5A400     −752
```

位移在 **−896 ~ +64** 之间**非均匀跳变**。

### 2.3 结论

```
同源重编译  vs  重写？
   ├─ .rsrc 相同偏移一致率 100%    ┐
   ├─ .data 相同偏移一致率 95.43%  ├─→ 数据段未变
   └─ .text 相同偏移一致率  5.78%  ┘
                                    │
                        .text 起始 128 字节几乎全同
                                    │
                                    ▼
                    结论：同源重编译，代码整体位移 + 局部增删
```

> **架构推论**：固定偏移迁移方案在跨版本时**必然失效**，必须改用 AOB 特征码扫描。

## 3. 跨版本位点迁移：滑动汉明距离

### 3.1 方法

用已知版本的位点为中心取 **64 字节窗口**，在目标版本上做**滑动汉明距离**匹配，取距离最小者。

```python
idx = np.arange(lo, hi)[:, None] + np.arange(WIN)[None, :]
dist = (A11[idx] != win[None, :]).sum(axis=1)
best = lo + int(dist.argmin())
```

**判据**：64 字节窗口下，随机匹配的期望汉明距离 ≈ **62**；实测命中距离 **1–6** ⇒ 置信度极高。

> ⚠️ **反例警示**：不要用「分块哈希锚点」建全局偏移映射 —— 大二进制中重复块会导致误锚定，实测产出了 `+1,755,424` 这种荒谬位移。**滑动汉明距离直接定位更可靠**。

## 4. 特征码生成：多版本共同稳定区

### 4.1 生成规则

1. 以位点为中心，**向左右扩展**，取所有已采集版本中**完全一致**的字节；
2. 生成**双态特征码**：原始态（含期望字节）/ 已补丁态（含补丁字节）；
3. **双态唯一性**校验：两份特征码在所有版本的「原始态 / 已补丁态」中均须**唯一命中**。

### 4.2 关键教训一：单版本特征码会混入重定位指针

用 **build 11.2 单版本**生成的特征码，在 **build 11.3** 上 **13/14 命中**，唯一失败的是「试用状态标志 + 天数常量」：

```
build 11.2 特征码右扩展 4 字节: 38 83 69 00
build 11.3 同位置:              30 83 69 00     ← 重定位指针，差 8
```

**修正**：改用 **build 10 / 11.2 / 11.3 三版本**共同稳定区 → 该点右扩展自动归零（长度 50 → 46）。

> **规则**：特征码扩展必须要求该字节在**所有已采集版本**中一致，否则会把版本相关的重定位指针、地址常量纳入特征码。

### 4.3 关键教训二：相邻位点必须合并

数据段两个位点相距仅 **4 字节**：

```
0x378CDC  01 00 00 00        ← 试用状态标志
0x378CE0          1E 00 00 00 ← 试用天数常量（30 天）
```

拆成两条时，**特征码互相包含** → 唯一性校验必然失败。
**修正**：合并为单条 8 字节条目：

```
01 00 00 00 1E 00 00 00   →   00 00 00 00 FF FF FF 7F
```

### 4.4 统计

- 总字节数 **755**，平均 **53.9 字节/位点**
- 最短 14 字节（看门狗关联函数），最长 118 字节（授权分支检测）

## 5. 语义验证：反汇编交叉印证

用 capstone 对每个位点做**三版本指令序列比对**（归一化掉地址与跳转目标）：

```python
md = Cs(CS_ARCH_X86, CS_MODE_32); md.syntax = CS_OPT_SYNTAX_INTEL
code = data[foff:foff + 24]
insns = [i.mnemonic + " " + i.op_str for i in md.disasm(code, va)]
```

### 5.1 最有价值的印证：全局地址咬合

「试用期计算」位点的指令序列：

```asm
mov eax, dword ptr [0x779CDC]    ; RVA 0x379CDC → 文件偏移 0x378CDC
neg eax
sbb eax, eax
and eax, 0xF                     ; ← 补丁点
add eax, 0xF                     ; ← 补丁点
mov dword ptr [0x779CE0], eax    ; RVA 0x379CE0 → 文件偏移 0x378CE0
```

**代码段指令引用的两个全局地址，恰好落在数据段两个补丁点的文件偏移上** —— 三点语义完全咬合，证明分析无误。

> 换算：`文件偏移 = 节区 RawPtr + (VA − ImageBase − 节区 VA)`
> `.data`：`0x378000 + (0x779CDC − 0x400000 − 0x379000) = 0x378CDC` ✓

### 5.2 三版本语义对比结论

| 补丁点 | 指令序列（归一化后） | 语义 |
|---|---|:--:|
| 授权分支检测 | `test eax,eax` \| `jne ADDR` \| `mov byte [ebp-0xAB1],1` | 三版相同 |
| 试用期最大值 | `and eax,0xF` \| `add eax,0xF` \| `mov [0x779CE0],eax` | **连全局地址都相同** |
| 假序列号弹窗 | `je ADDR` \| `cmp byte [esp+7],0` \| `jne ADDR` | 三版相同 |
| 守护线程 A–F | `push -1` \| `push <SEH表>` \| `mov eax,fs:[0]` | 仅 SEH 表地址重定位 |
| 守护线程 E | `push ebp` \| `mov ebp,esp` \| `and esp,0xFFFFFFF8` | 三版相同 |
| 过期强退 | `jne ADDR` \| `call ADDR` \| `test eax,eax` | 三版相同 |

> **结论**：目标程序本次更新对**授权校验机制本身零变更**，差异仅为代码位置平移与重定位地址。

### 5.3 发现：COMDAT 折叠导致的特征码锚定问题

「守护线程 D」与「看门狗关联函数」的**前 24 字节逐字节相同**，且**共享同一 SEH 作用域表**：

```
守护线程 D      @0x7CA50: 6A FF 68 9C 8D 66 00 64 A1 00 00 00 00 50 81 EC C4 01 00 00 ...
看门狗关联函数   @0x834E0: 6A FF 68 9C 8D 66 00 64 A1 00 00 00 00 50 81 EC C4 01 00 00 ...
                          └──────────── 完全相同 ────────────┘
```

**成因**：链接器 **COMDAT 折叠**合并了同一模板实例的 SEH 作用域表。

**影响**：这两个位点的特征码**无法依赖函数序言**（序言相同会双命中），只能靠**左侧前一个函数的尾部字节**锚定 —— 其中「看门狗关联函数」的特征码仅 **14 字节**（最短的一条）。

> **风险提示**：若未来版本中该锚定区发生变化，需重新采集。

## 6. 工程保障（防写坏设计）

### 6.1 PE 结构门禁

解析 PE 头，动态求出一切关键偏移：

```
e_lfanew   = DWORD @ 0x3C
COFF       = e_lfanew + 4
Optional   = COFF + 20
CheckSum   = Optional + 0x40
DataDir[4] = Optional + 0x60 (PE32) / 0x70 (PE32+)
ImageEnd   = max(节区 RawPtr + RawSize)
```

**校验**：MZ / PE 签名 / 节区边界 / `RawPtr + RawSize ≤ 文件长度`。
**任一不合法 → 立即拒绝**（这正是「非有效 Win32 程序」的判据）。

### 6.2 安全截断

只剥离「**超出 `ImageEnd` 且长度 == `SecuritySize`**」的 Authenticode 尾部 —— 彻底替代硬编码 `6189056`。

### 6.3 PE 校验和标准化

补丁与截断完成后，用**微软标准算法**重算：

```python
def pe_checksum(data, off):
    t = 0
    for i in range(0, len(data)-1, 2):
        w = 0 if (off <= i < off+4) else (data[i] | (data[i+1] << 8))
        t += w; t = (t & 0xFFFF) + (t >> 16)
    while t > 0xFFFF: t = (t & 0xFFFF) + (t >> 16)
    return (t + len(data)) & 0xFFFFFFFF
```

**反直觉发现**：原版 Crack 写入的 `0x005F0BEA` **经穷举验证不属于任何标准算法**（4 种输入状态 × 16 种算法变体均无法复现），而官方原版的校验和与标准算法 **100% 吻合**。

> 它能工作 ⇒ 目标程序与 Windows **均不校验该字段**。本工具改为写入**正确值**。

### 6.4 版本感知备份（防止升级后回滚点错版）

用户升级后，目录中遗留的备份仍属**上一版本**：

| 情形 | 处理 |
|---|---|
| BAK 不存在 | 直接备份 |
| BAK 版本 == 当前版本 | 保持不变 |
| BAK 版本 ≠ 当前版本，当前为纯净原版 | 旧备份归档为 `项目D.exe.BAK.<旧版本>`，写入新备份 |
| BAK 版本 ≠ 当前版本，当前已含补丁 | **拒绝继续** |

并为「一键还原」加入**版本一致性守卫**。

> 💥 **该守卫在回归测试中当场拦下一次真实事故** —— 测试误触真实安装目录时，正是它阻止了旧版本主程序覆盖新版本安装。

### 6.5 原子写入 + 三级回滚

```
写前建 .rollback.tmp
  → 写入前 PE 终检
    → 写临时文件
      → 落盘后复读并重新解析 PE
        → 失败自动回滚
```

### 6.6 差异字节白名单

产物相对原版的**每一个差异字节**，必须落在「补丁位点 ∪ PE 校验和 ∪ 签名目录」内：

```csharp
HashSet<int> expected = ...;   // 全部预期改动偏移
foreach (int o in diffs)
    if (!expected.Contains(o)) → 判定为「意外改动」，测试失败
```

## 7. 运行时定位：当静态追踪撞上 vtable 间接调用

> 本轮修复的核心方法论增量。静态特征码扫描能定位**已知位点**，
> 但当目标是「**谁在什么条件下弹出这个窗口**」时，静态分析会陷入间接调用的泥潭。

### 7.1 静态路径为何走不通

目标窗口是 Win32 对话框资源，理论上可从资源目录反查调用点：

| 尝试 | 结果 |
|---|---|
| 搜索对话框字符串 | **全部失败** —— 资源为英文(1033)，中文来自语言包；注册表键名亦被加密 |
| 反汇编 `CreateDialogIndirectParamA` 调用点 | 仅 1 处 —— 说明对话框由**统一入口**动态构造 |
| 反查对话框资源 ID 的写入点 | **0 处** —— ID 经 vtable 传递，无 `call rel32` |
| 搜索 `call <弹框函数>` | 4 处调用点，但无法判定哪一处是启动路径 |

**卡点本质**：x86 逆向中，成员函数经 vtable / 函数指针传递时，
静态 xref 会彻底断裂。此时继续静态推演性价比极低。

### 7.2 破局：动态插桩直接抓调用栈

用 Frida 附加目标进程，在**统一对话框入口**下钩子，打印模板标题 + 回溯栈：

```javascript
var user32 = Process.getModuleByName("user32.dll");
var api = user32.getExportByName("CreateDialogIndirectParamA");
Interceptor.attach(api, {
  onEnter: function (args) {
    console.log("TITLE=" + JSON.stringify(dumpTitle(args[1])));
    Thread.backtrace(this.context, Backtracer.FUZZY).slice(0, 16).forEach(function (a) {
      var m = modOf(a);
      console.log("   " + a + "  " + m.name + "+0x" + a.sub(m.base).toString(16));
    });
  }
});
```

**关键技巧：静态 VA 换算**

模块基址随 ASLR 浮动，需把静态 VA 换算成运行时地址：

```javascript
var delta = Process.enumerateModules()[0].base.sub(ptr("0x400000"));
function staticAddr(va) { return ptr(va).add(delta); }
```

**输出（一次命中）**：

```
TITLE="Internet Download Manager Registration"
  0x612A0A   CreateDialogIndirectParamA 内部
  0x618D12
  0x62F293
  0x612BB1   DoModal 包装
  0x62D971
  0x489683   ← ★ 触发点（即 call 0x612aac 的下一条指令）
  0x669DCB   ← 该函数的 SEH handler（回溯栈噪声，需排除）
  0x48E276   ← 真正的调用者
```

> **陷阱**：MSVC 的 SEH handler 地址会被压栈，回溯时**会混入栈帧**，

### 7.5 假阳性排除纪律

修复上线前必须做**对照组实验**，否则会把测试方法的副作用误判为产品缺陷。

|---|---|---|---|

## 8. build 15 迁移：静默自动更新 + 填充漂移（v1.5.0）

### 8.1 失效现象与根因链

用户报告「新版本出现特权状态离线验证失败」。现场勘察结果：

| 观测项 | 值 | 含义 |
|---|---|---|
| `项目D.exe` 版本 | **6.43.15.3**（6,201,712 B） | 已被官方更新器替换 |
| 签名目录 | RVA `0x5E7800` / 10,608 B | **签名完整 ⇒ 纯净原版，补丁全丢** |
| `idmvers` | `v6.43b15 Trial` | 特权态回落试用 |
| `Serial` | 不存在 | 授权键被清空 |

**根因链**：官方内置更新器静默下载新版 → 覆盖已打补丁的主程序 →
旧引擎特征码仅覆盖 b10/11.2/11.3 → 扫描 **5/15 命中** → 按设计**熔断拒绝写入**。

> 这一步恰恰证明了 **fail-closed 设计的价值**：引擎没有硬套旧偏移，
> 否则会把 b15 的代码段写坏，用户拿到的将是**彻底无法启动**的二进制。

### 8.2 五版本共同稳定区收窄

把新样本加入特征码生成器的版本列表后，`grow()` 函数的左右扩展立即在更多位置停止 ——
因为要求**所有版本字节一致**，可用区间必然收缩：

| 位点 | 三版本特征码 | 五版本特征码 |
|---|---|---|
| 授权分支检测 | 118 B | **24 B** |
| 守护线程 F | 80 B | **29 B** |
| 试用期最大值 | 90 B | **13 B** |
| 特征码总字节 | ~1,050 B | **378 B** |

> 这是**结构性权衡**：版本越多，共同稳定区越小。
> 但**双态唯一性（1/1）仍是硬判据** —— 只要唯一命中 + 期望字节复核，
> 短特征码在工程上依然安全（引擎在运行时还会再次校验命中数 == 1）。

### 8.3 关键教训：模糊匹配只能产生「候选」，不能作为结论

本轮唯一翻车的位点是 **#14 试用标志 + 天数常量**。

```
b11.3/b12.3 : … 6E 74 73 40 40 │ 00 00 00       │ 01 00 00 00 │ 01 00 00 00 │ 1E 00 00 00 …
b15.3       : … 6E 74 73 40 40 │ 00 00 00 00 00 │ 01 00 00 00 │ 01 00 00 00 │ 1E 00 00 00 …
                                      ↑ 多出 2 个零填充字节
```

滑动汉明距离给出 **汉明距离 = 2** 的「极佳匹配」，
按「≤ 8 即命中」的判据完全合格 —— 但位置**早了 2 字节**，
给出的补丁偏移 `0x379546` 处字节是 `01 00 00 00 01 00 00 00`，
而期望是 `01 00 00 00 1E 00 00 00`（缺 `1E`）。

**为什么会错**：该数据块的「尾部」在多版本间高度一致，
而「头部填充」发生了位移；汉明距离对**整体相似度**敏感，
对**结构对齐**不敏感。填充类位移是它的天然盲区。

**修正流程（已固化进 `tools/`）**：

1. 模糊匹配只用于**产生候选位置**；
2. 候选位置必须通过 **期望字节精确匹配**；
3. 不通过时，改用**精确锚点搜索**（本例：`AVCDownloadComponents` 字符串 + 常量对）；
4. 最终必须经 **capstone 反汇编语义对照**确认与基线一致。

> 本例正确偏移 **`0x379524`**，由精确锚定 + 反汇编双确认得到。

### 8.4 可复用纪律（本案例沉淀）

| # | 纪律 | 来源 |
|---|---|---|
| 1 | 跨版本定位必须「模糊候选 → 精确字节 → 反汇编语义」三重确认 | §8.3 |
| 2 | 数据段位点尤其危险：填充、对齐、常量池都可能非均匀漂移 | §8.3 |
| 3 | 特征码必须基于**全部已采集版本**的共同稳定区重新生成 | §4.2 / §8.2 |
| 4 | 引擎必须 fail-closed：任一必需位点未命中即**零字节写入** | §8.1 |
| 5 | 每次扩展版本都要断言**既有版本产物哈希零变化** | §8.2 |
| 6 | 客户侧加固：关闭自动更新，避免静默升级冲掉本地特权态 | §8.1 |

### 9.1 失效现象与悖论

用户反馈：必须在工具中**关闭屏蔽更新**才能正常使用；开启屏蔽更新后，项目D 启动或下载时频发报错：

这导致「屏蔽更新」功能陷入两难：开启则下载被阻断，关闭则会被静默升级冲掉激活。

### 9.2 逆向发现与传闻纠偏

通过 Frida 监控注册表访问结合静态反汇编分析，得出三项定性结论：

1. **`CheckUpdtVM = 0` 纯属民间传闻**：
   全二进制搜索证实，`项目D.exe` **从来不会读取 `CheckUpdtVM`**！

   所谓「写 0 屏蔽更新」从底层代码逻辑看是**完全不存在的伪配置**。
2. **`LastCheckQU` 清理的严重副作用**：
   旧激活工具误将 `LastCheckQU` 视为黑名单追踪键予以删除。
   但实测证实该键全称为 **Last Check Quick Update**（上次快速更新时间戳）。
   该键被删除后，项目D 启动即判定「从未进行过快速更新」，从而**在启动时立即强行向官方服务器发起后台更新查询**！
3. **后台更新撞死代理**：
   强行发起的后台更新查询尝试通过 WinINET 系统代理连接官方服务器。
   若用户代理软件未运行、端口变动或关闭，后台更新连接立即失败，触发 项目D 全局错误机制**弹出代理连接失败报错对话框**。

### 9.3 架构级根治（位点 16）

定位 项目D 启动总控逻辑中的更新定时器安装点：

| 版本 | 文件偏移 | 原始指令 | 修补指令 | 语义 |

| build 11.2 | `0x7689D` | `75 19` | `EB 19` | 跳过 `SetTimer` |
| build 11.3 | `0x7683D` | `75 19` | `EB 19` | 跳过 `SetTimer` |

### 10.1 失效现象与第一判断

官方静默更新到 build 16 后，已激活环境重新弹出注册对话框（资源 ID 138）。

**第一判断：先确认是「引擎拒绝写入」，而不是「新增反篡改」。**

用 v1.6.0 的五版本特征码表扫描 build 16.3 → **16 个位点仅命中 5 个** → fail-closed 引擎**零字节写入** → 二进制保持官方原版 → 权益回落 `v6.43b16 Trial` → 启动弹框。

> 用户看到的是「弹框」，根因却是「补丁没打上」。
> **排查顺序必须是：先看引擎日志命中数，再看目标行为。** 反过来会误判成厂商新增了对抗。

### 10.2 结构差异量化：这不是小版本

| 节区 | b15.3 VSize | b16.3 VSize | 变化 |
|---|---:|---:|---:|
| `.text` | `0x2931FC` | `0x2D05EC` | **+250,864 B（+245 KB）** |
| `.rdata` | `0xE500E` | `0xEB79A` | +26,508 B |
| `.data` | `0x136DC` | `0x1407C` | +2,464 B |
| `.rsrc` | `0x22D738` | `0x22D738` | **±0** |

| 4 | 守护线程 A | `0x74A10` | `0x74FA0` | +1424 | 5 | `6A` ✓ |

### 10.4 语义验证：capstone 的正确用法

**方法修正（踩坑）**：最初的实现是对 `.text` 段做**线性反汇编**并建地址索引表。结果 2.9 MB 只产出 39,100 条指令（≈74 B/指令，正常应 3–4 B/指令）——说明 capstone 在遇到不可解码字节时**提前停止**，线性扫描早已失步。

**正确做法：局部定向反汇编**

```python
def find_boundary(d, secs, patch_fo):
    va_patch = foff2va(secs, patch_fo)
    for back in range(0, 16):                      # 多个候选起点
        va0 = va_patch - back
        fo0 = va2foff(secs, va0)
        for ins in md.disasm(d[fo0:fo0+64], va0):
            if ins.address == va_patch:            # 恰好起始于补丁地址
                return ins.mnemonic, ins.op_str, bytes(ins.bytes)
            if ins.address > va_patch:
                break
```

**结果**：15 个代码位点在 b15.3 与 b16.3 中全部命中指令边界，且助记符完全一致：

| 位点类型 | b15.3 | b16.3 |
|---|---|---|
| 授权分支 | `test eax, eax` `[85C0]` | 同 |
| 试用期最大值 | `and eax, 0xf` `[83E00F]` | 同 |
| 假序列号弹窗 A/B | `je 0x…` `[742A]` | 同 |
| 守护线程 A–D/F、看门狗 | `push -1` `[6AFF]` | 同 |
| 守护线程 E | `push ebp` `[55]` | 同 |
| 过期强退 | `jne 0x…` `[0F85D2010000]` | 同 |
| 注册对话框抑制 | `je 0x…` `[740C]` | 同 |
| 更新定时器切断 | `jne 0x…` `[7519]` | 同 |

#### 位点 12 的特殊性：操作数补丁 ≠ 操作码补丁

上下文（补丁地址 ±12 字节）：

```
B8 01 00 00 00 9B E9 D5 00 00 00 B8 [01] 00 00 00 A3 …
                                      ↑ 补丁点
```

`B8 01 00 00 00` = `mov eax, 1`。补丁字节落在**立即数**上（`01` → `00`），不是操作码。

> **教训**：验证逻辑若一律要求「补丁地址 == 指令起始地址」，会把这类**操作数补丁**误报为「未对齐」。
> 必须在位点定义里显式区分两类：
> - **操作码补丁**（改 `jz`→`jmp`、`push`→`ret`）：要求落在指令边界
> - **操作数补丁**（改立即数/位移）：要求落在**所属指令的字节范围内**，并核对 opcode 不变

### 10.5 六版本特征码重生成

纳入 build 16 后，共同稳定区进一步收窄。最典型的证据：

**位点 1 左侧的 `0x69` 在 build 16 变为 `0x6D`。**

```
b15.3:  … 04 20 6D 00 [69] 00 85 C0 …    ← FF 15 04 20 6D 00 = call [0x006D2004]
b16.3:  … 04 20 6D 00 [6D] 00 85 C0 …
```

那 4 字节是 IAT 间接调用的**绝对地址常量**，随代码重排而变。六版本交集因此只保留 `0x00` 一字节，左扩展由 2 B 自动收缩为 1 B——**这正是「多版本共同稳定区」机制在按设计工作**。

#### 签名长度上限：一个必须显式做出的工程取舍

| 策略 | 总字节 | 平均 | 位点 16 长度 | 风险 |
|---|---:|---:|---:|---|
| 最大扩展 | 502 B | 31.4 B | 135 B | 过度特化，未来版本极易失配 |
| 最短充分 | 142 B | 8.9 B | 5 B | 4–6 B 签名，**误命中风险** |
| **上限 48 B（选定）** | **366 B** | **22.9 B** | **48 B** | **平衡** |

**判据**：两种失败模式的严重性不对等——

| 失败模式 | 后果 | 严重性 |
|---|---|---|
| 签名过短 → 误命中错误位置 | **写坏二进制** | 🔴 致命 |
| 签名过长 → 新版本失配 | 干净中止，零字节写入 | 🟢 可恢复 |

因此策略是：**优先保证「不误命中」，同时用 48 B 上限约束「不过度特化」**。
下限由双态唯一性（1/1）硬门禁保证，上限由工程经验设定。

### 10.6 零回归与双实现交叉验证

**零回归**：五版本（b10 / 11.2 / 11.3 / 12.3 / 15.3）的修补产物 SHA-256 与 v1.5.1 **逐字节一致**。

**双实现交叉验证**：C# 引擎与独立 Python 参考实现各自对 build 16.3 打补丁，产出同一哈希：

```
C# 引擎        : 8F77A3E8099F191C165E7733618B3DEAA702FFFC4D392696ECDDB555A029B5EE
Python 参考实现 : 8F77A3E8099F191C165E7733618B3DEAA702FFFC4D392696ECDDB555A029B5EE
```

> **为什么值得做**：两套独立实现只要有一处对「补丁偏移 / 截断时机 / 校验和算法」的理解不同，哈希就会分叉。
> 同哈希是补丁语义正确的强证据，比任何单侧自测都可靠。

### 10.7 差异字节白名单审计

| 项 | 数量 |
|---|---:|
| 重叠区差异字节 | **32** |
| 其中：补丁位点 | 26 |
| 其中：PE 校验和字段 | 2 |
| 其中：签名目录（8 B 中实际非零的） | 4 |
| 尾部截断（Authenticode 签名） | 10,608 B |
| **白名单外差异** | **0** |

### 10.8 关键教训汇总

| # | 教训 | 一句话 |
|---|---|---|
| 1 | **先查引擎，再查目标** | 弹框可能是「补丁没打上」而非「新增对抗」 |
| 2 | **位移非均匀，禁止全表平移** | 段内 delta 可从 +464 变到 +1424 |
| 3 | **线性反汇编会失步** | capstone 遇不可解码字节即停，必须用局部定向反汇编 |
| 4 | **区分操作码补丁与操作数补丁** | 位点 12 打在立即数上，硬套「指令边界」判据会误报 |
| 5 | **签名长度要显式设上限** | 误命中=写坏二进制；失配=干净中止。两者严重性不对等 |
| 6 | **双实现交叉验证哈希** | 同哈希是补丁语义正确的强证据 |
| 7 | **`.rsrc` 不变是关键线索** | 排除「厂商换对话框」，锁定代码路径 |

## 11. build 18 迁移：零漂移吸收与 48 字节上限的回报（v1.6.2）

> 这是本项目历史上**第一次以零字节签名表改动**吸收的新版本。
> 价值不在「又支持了一个版本」，而在「证明了适配成本可以降到零」。

### 11.1 失效现象

官方静默更新 6.43.16.3 → **6.43.18.3**（build 17 被整版跳过）。更新后：

- **注册对话框**（资源 ID 138）重新弹出；
- **试用倒计时弹窗**同时回归；
- `idmvers` 回落为 `v6.43b18 Trial`。

症状与 build 15 / build 16 完全同源：官方更新器替换 `IDMan.exe`，
而全部授权裁决仍在客户端完成（CWE-602）。

### 11.2 结构差分：方向翻转的重排

| 节区 | build 16.3 | build 18.3 | 增量 |
|---|---:|---:|---:|
| `.text` RawSize | `0x2D0600` | `0x2D6600` | **+24,576** |
| `.rdata` RawSize | `0xEB800` | `0xEBE00` | +1,536 |
| `.data` RawSize | `0xA800` | `0xA800` | **±0** |
| `.rsrc` RawSize | `0x22D800` | `0x22D800` | **±0** |
| `.reloc` RawSize | `0x39E00` | `0x3A000` | +512 |
| 文件体积 | 6,490,480 | 6,517,104 | +26,624 |

全部节区 VA 整体后移 `+0x6000`（`.text` 仍自 `0x1000` 起始）。

**关键差异 —— 段内位移方向翻转**：

| 版本跨度 | 代码段位移 | 数据段位移 |
|---|---|---|
| build 15.3 → 16.3 | `+0x1D0` ~ `+0x5E0`（全正） | `+0x43A00` |
| **build 16.3 → 18.3** | **`−0x320` ~ `−0x9A0`（全负）** | **`+0x6600`** |

位移方向翻转是签名匹配里较难的情形：漂移朝与上次标定**相反**的方向累积，
任何「按上一版本 delta 趋势外推」的策略都会失效。

### 11.3 定位结果：16/16 精确命中，汉明 0

### 11.4 48 字节上限为什么扛住了 2.4 KB 位移

build 18 的最大代码位移（`−0x9A0` ≈ 2.5 KB）**大于** build 16（`+0x5E0` ≈ 1.5 KB），
签名表却原封不动地存活。这不是运气，是 v1.6.1 期间那个决策的直接兑现：

| 方案 | 全表体积 | 平均长度 | 风险 |
|---|---:|---:|---|
| 最小充分（仅覆盖 6 版本差异） | 142 B | 8.9 B | **误命中 → 写坏二进制** |
| 最大扩展（吃到 64 B 窗口边界） | 502 B | 31.4 B | 漂移脆弱 → 每版必重建 |
| **选定的 48 B 上限** | **366 B** | **22.9 B** | 两侧风险均被压低 |

签名的作用是「在噪声中唯一定位」：太短会被无关字节序列命中，
太长会被版本漂移切断。48 B 提供的上下文足以跨越 2.5 KB 的跨版本位移，
同时保持足够熵值（22.9 B 平均 ⇒ 碰撞概率远低于实用阈值）。

> **教训**：签名长度的选择应显式设界并记录理由。
> 「能匹配就行、越短越好」是一个会在未来版本上反噬的隐性债务。

### 11.5 语义复核（仍然全做）

即使精确命中，也**不能跳过**语义验证 —— 命中只证明字节一致，不证明语义未变。

| 校验项 | 结果 |
|---|---|
| 指令边界 | 15 个代码位点全部落在指令边界 |
| 助记符/操作数 | `test eax,eax` / `and eax,0xf` / `push -1` / `push ebp` / `je` / `jne` —— 与 build 16 完全一致 |
| 位点 12 操作数补丁 | `0x995F0` 处 `mov eax,1`（`B8 01 00 00 00`），补丁字节位于 `+1` → `mov eax,0` ✓ |
| `.data` 常量块 | `010000001E000000` 逐字节相同 |

位点 12 再次提醒：**该位点不在指令边界上**。
若把「必须起始于指令边界」当作硬判据，会得到 `add dword ptr [eax], eax` 这类
错位反汇编结果并误报失败 —— 正确做法是「找出**包含**该偏移的指令」，
再验证补丁字节是否落在立即数字段内。

### 11.6 反篡改取证：确认没有新增对抗

对 build 16 / build 18 做 UTF-16 资源字符串差分，新增仅 **10 条**：

| 新增字符串 | 性质 |
|---|---|
| `6, 43, 18, 3` | 版本号 |
| `f%s%sSounds\%s` | 音效路径模板 |
| `f / Socks...` | SOCKS 对话框片段 |
| `gnlaapi.dll` | 第三方组件名 |
| `fTLS13_OFF` | 标志名 |
| `gEnglish` | 语言标识 |
| 其余 4 条 | 短 ASCII 噪声 |

**无一与授权、试用、更新相关**。结论：build 18 **未引入任何新防御机制**，
失效纯粹源于二进制重排。

### 11.8 关键教训汇总

| # | 教训 | 一句话 |
|---|---|---|
| 1 | **先做精确命中预检** | 汉明搜索是兜底，不是首选；跳过它可以直接省掉整条重生成流水线 |
