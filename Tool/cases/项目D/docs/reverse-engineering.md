# 逆向过程记录（项目D · 授权校验链跨版本迁移）

> 目标：项目D 6.43 build 10 → build 11（6.43.11.2 / 6.43.11.3）
> 完整过程见工作区 case 目录（不随本仓库发布）；本文保留可复现的方法论与关键命令。

---

## 0. 问题背景：一次架构倒退

### 0.1 现象

用户反馈：执行「写入授权」后启动目标程序，弹出

```
System.ComponentModel.Win32Exception (0x80004005):
指定的可执行文件不是此操作系统平台的有效应用程序
```

调用栈指向 `Process.StartWithShellExecuteEx`，即 **PE 映像已被写坏**（Win32 错误 193 / `ERROR_BAD_EXE_FORMAT`）。

### 0.2 根因

第二代工具把补丁位点**硬编码为 build 10 专属的绝对文件偏移**，并**无条件把文件截断到 6,189,056 字节**：

```csharp
const int TARGET_FILE_SIZE = 6189056;      // build 10 专属常量
if (data.Length > TARGET_FILE_SIZE)        // 只看「比目标大」，完全不校验版本
    Array.Resize(ref data, TARGET_FILE_SIZE);
```

`6189056` 恰好等于 build 10 的节区表末尾（`0x5E7000`），被砍掉的 10,608 字节正是 Authenticode 签名 —— 对 build 10 是**正确的**。

但任何**体积更大的版本**走到这里，就会被拦腰砍断 `.rsrc` / `.reloc` 节区的原始数据 → PE 加载器直接拒绝。

### 0.3 架构演进对照

| 代 | 定位方式 | 跨版本 | 结果 |
|:--:|---|:--:|---|
| Gen 1 | **AOB 特征码搜索**（12 条） | ✅ | 可用 |
| Gen 2 | 硬编码绝对偏移（18 点 / 31 字节） | ❌ | **写坏映像** ← 本案例起点 |
| Gen 3 | 硬编码偏移 + PE 解析门禁 | ❌ | 不再写坏，但仍仅支持单版本 |
| **Gen 4** | **AOB 双态特征码**（14 条 / 3 版本验证） | ✅ | 本案例成果 |

> **核心教训**：Gen 2 为了「更精确」把特征码搜索降级成写死偏移，用一个隐含的版本假设换取了短期精确性。

## 1. 安装包拆解（自定义 SFX）

官方安装包是**自定义 SFX**：PE 本体仅 95,232 字节，其余 12,457,696 字节为 overlay。

### 1.1 条目格式（逆向确认）

```
[0x00] DWORD  原始大小 (uncompressed size)
[0x04] DWORD  压缩大小 (compressed size)
[0x08] FILETIME × 3
[0x20] zlib 流 (deflate, 78 DA)
```

链式排列：`next = cur + 0x20 + compressedSize`

### 1.2 提取

```python
pos = 0
while pos + 0x20 <= len(overlay):
    d0, d1 = struct.unpack_from('<II', overlay, pos)      # 原始/压缩大小
    data = zlib.decompress(overlay[pos + 0x20:])          # 解压载荷
    pos = pos + 0x20 + d1
```

**校验手段**：安装脚本（第一个条目）内含 `<P<n>="文件名">` 清单，与载荷顺序**逐条精确对齐** —— 用已知体积（`idman.chm` = 320,931、`idmantypeinfo.tlb` = 2,596）交叉验证映射正确。

结果：192 个条目全部解出，主程序位于**条目 #5**（压缩 2,602,327 → 解压 6,200,176 字节）。

> ⚠️ **踩坑**：安装包内是 **6.43.11.2**，而实际安装的是 **6.43.11.3**（体积相同、SHA256 不同）。必须**以真实安装文件为分析对象**，不能只信安装包。

## 2. 版本差异性质判定

### 2.1 相似度矩阵（按节区，相同偏移逐字节比对）

| 节区 | build 10 vs build 11 |
|---|---|
| `.rsrc` | **100.00%** 相同 |
| `.data` | **95.43%** 相同 |
| `.rdata` | 38.33% 相同 |
| `.reloc` | 35.45% 相同 |
| `.text` | **5.78%** 相同 |

`.text` 仅 5.78% 看似「重写」，但：

```
build 10  @0x400: 8B 44 24 04 83 F8 50 77 13 ... E9 F3 F9 20 00 E9 26 FA 20 00 C3
build 11  @0x400: 8B 44 24 04 83 F8 50 77 13 ... E9 03 FC 20 00 E9 36 FC 20 00 C3
                                                   └─ 仅 E9 rel32 目标不同 ─┘
```

跳转目标差 `+0x210` = `.text` VSize 增长量 ⇒ **代码整体位移，而非重写**。

### 2.2 位移曲线

以 64 字节窗口、4KB 步长，在 `±0x8000` 范围内搜索最佳匹配：

```
b10 RVA     位移      说明
0x400       +0        节区起点对齐
0x2400      +64       首次插入
0xD400      −608      删除
0x10400     −880      稳定区间
0x21400     −608
0x2F400     −144      大幅插入后回落
0x34400     −368
0x5A400     −752
```

位移在 **−896 ~ +64** 之间**非均匀跳变**。

### 2.3 结论

```
同源重编译  vs  重写？
   ├─ .rsrc 相同偏移一致率 100%    ┐
   ├─ .data 相同偏移一致率 95.43%  ├─→ 数据段未变
   └─ .text 相同偏移一致率  5.78%  ┘
                                    │
                        .text 起始 128 字节几乎全同
                                    │
                                    ▼
                    结论：同源重编译，代码整体位移 + 局部增删
```

> **架构推论**：固定偏移迁移方案在跨版本时**必然失效**，必须改用 AOB 特征码扫描。

## 3. 跨版本位点迁移：滑动汉明距离

### 3.1 方法

用已知版本的位点为中心取 **64 字节窗口**，在目标版本上做**滑动汉明距离**匹配，取距离最小者。

```python
idx = np.arange(lo, hi)[:, None] + np.arange(WIN)[None, :]
dist = (A11[idx] != win[None, :]).sum(axis=1)
best = lo + int(dist.argmin())
```

**判据**：64 字节窗口下，随机匹配的期望汉明距离 ≈ **62**；实测命中距离 **1–6** ⇒ 置信度极高。

> ⚠️ **反例警示**：不要用「分块哈希锚点」建全局偏移映射 —— 大二进制中重复块会导致误锚定，实测产出了 `+1,755,424` 这种荒谬位移。**滑动汉明距离直接定位更可靠**。

### 3.2 结果

|---|---|---|---|---|
| 授权分支检测 | 0x2D7BD | 0x2D45D | −864 | 2 |

## 4. 特征码生成：多版本共同稳定区

### 4.1 生成规则

1. 以位点为中心，**向左右扩展**，取所有已采集版本中**完全一致**的字节；
2. 生成**双态特征码**：原始态（含期望字节）/ 已补丁态（含补丁字节）；
3. **双态唯一性**校验：两份特征码在所有版本的「原始态 / 已补丁态」中均须**唯一命中**。

### 4.2 关键教训一：单版本特征码会混入重定位指针

用 **build 11.2 单版本**生成的特征码，在 **build 11.3** 上 **13/14 命中**，唯一失败的是「试用状态标志 + 天数常量」：

```
build 11.2 特征码右扩展 4 字节: 38 83 69 00
build 11.3 同位置:              30 83 69 00     ← 重定位指针，差 8
```

**修正**：改用 **build 10 / 11.2 / 11.3 三版本**共同稳定区 → 该点右扩展自动归零（长度 50 → 46）。

> **规则**：特征码扩展必须要求该字节在**所有已采集版本**中一致，否则会把版本相关的重定位指针、地址常量纳入特征码。

### 4.3 关键教训二：相邻位点必须合并

数据段两个位点相距仅 **4 字节**：

```
0x378CDC  01 00 00 00        ← 试用状态标志
0x378CE0          1E 00 00 00 ← 试用天数常量（30 天）
```

拆成两条时，**特征码互相包含** → 唯一性校验必然失败。
**修正**：合并为单条 8 字节条目：

```
01 00 00 00 1E 00 00 00   →   00 00 00 00 FF FF FF 7F
```

### 4.4 统计

- 总字节数 **755**，平均 **53.9 字节/位点**
- 最短 14 字节（看门狗关联函数），最长 118 字节（授权分支检测）

## 5. 语义验证：反汇编交叉印证

用 capstone 对每个位点做**三版本指令序列比对**（归一化掉地址与跳转目标）：

```python
md = Cs(CS_ARCH_X86, CS_MODE_32); md.syntax = CS_OPT_SYNTAX_INTEL
code = data[foff:foff + 24]
insns = [i.mnemonic + " " + i.op_str for i in md.disasm(code, va)]
```

### 5.1 最有价值的印证：全局地址咬合

「试用期计算」位点的指令序列：

```asm
mov eax, dword ptr [0x779CDC]    ; RVA 0x379CDC → 文件偏移 0x378CDC
neg eax
sbb eax, eax
and eax, 0xF                     ; ← 补丁点
add eax, 0xF                     ; ← 补丁点
mov dword ptr [0x779CE0], eax    ; RVA 0x379CE0 → 文件偏移 0x378CE0
```

**代码段指令引用的两个全局地址，恰好落在数据段两个补丁点的文件偏移上** —— 三点语义完全咬合，证明分析无误。

> 换算：`文件偏移 = 节区 RawPtr + (VA − ImageBase − 节区 VA)`
> `.data`：`0x378000 + (0x779CDC − 0x400000 − 0x379000) = 0x378CDC` ✓

### 5.2 三版本语义对比结论

| 补丁点 | 指令序列（归一化后） | 语义 |
|---|---|:--:|
| 授权分支检测 | `test eax,eax` \| `jne ADDR` \| `mov byte [ebp-0xAB1],1` | 三版相同 |
| 试用期最大值 | `and eax,0xF` \| `add eax,0xF` \| `mov [0x779CE0],eax` | **连全局地址都相同** |
| 假序列号弹窗 | `je ADDR` \| `cmp byte [esp+7],0` \| `jne ADDR` | 三版相同 |
| 守护线程 A–F | `push -1` \| `push <SEH表>` \| `mov eax,fs:[0]` | 仅 SEH 表地址重定位 |
| 守护线程 E | `push ebp` \| `mov ebp,esp` \| `and esp,0xFFFFFFF8` | 三版相同 |
| 过期强退 | `jne ADDR` \| `call ADDR` \| `test eax,eax` | 三版相同 |

> **结论**：目标程序本次更新对**授权校验机制本身零变更**，差异仅为代码位置平移与重定位地址。

### 5.3 发现：COMDAT 折叠导致的特征码锚定问题

「守护线程 D」与「看门狗关联函数」的**前 24 字节逐字节相同**，且**共享同一 SEH 作用域表**：

```
守护线程 D      @0x7CA50: 6A FF 68 9C 8D 66 00 64 A1 00 00 00 00 50 81 EC C4 01 00 00 ...
看门狗关联函数   @0x834E0: 6A FF 68 9C 8D 66 00 64 A1 00 00 00 00 50 81 EC C4 01 00 00 ...
                          └──────────── 完全相同 ────────────┘
```

**成因**：链接器 **COMDAT 折叠**合并了同一模板实例的 SEH 作用域表。

**影响**：这两个位点的特征码**无法依赖函数序言**（序言相同会双命中），只能靠**左侧前一个函数的尾部字节**锚定 —— 其中「看门狗关联函数」的特征码仅 **14 字节**（最短的一条）。

> **风险提示**：若未来版本中该锚定区发生变化，需重新采集。

## 6. 工程保障（防写坏设计）

### 6.1 PE 结构门禁

解析 PE 头，动态求出一切关键偏移：

```
e_lfanew   = DWORD @ 0x3C
COFF       = e_lfanew + 4
Optional   = COFF + 20
CheckSum   = Optional + 0x40
DataDir[4] = Optional + 0x60 (PE32) / 0x70 (PE32+)
ImageEnd   = max(节区 RawPtr + RawSize)
```

**校验**：MZ / PE 签名 / 节区边界 / `RawPtr + RawSize ≤ 文件长度`。
**任一不合法 → 立即拒绝**（这正是「非有效 Win32 程序」的判据）。

### 6.2 安全截断

只剥离「**超出 `ImageEnd` 且长度 == `SecuritySize`**」的 Authenticode 尾部 —— 彻底替代硬编码 `6189056`。

### 6.3 PE 校验和标准化

补丁与截断完成后，用**微软标准算法**重算：

```python
def pe_checksum(data, off):
    t = 0
    for i in range(0, len(data)-1, 2):
        w = 0 if (off <= i < off+4) else (data[i] | (data[i+1] << 8))
        t += w; t = (t & 0xFFFF) + (t >> 16)
    while t > 0xFFFF: t = (t & 0xFFFF) + (t >> 16)
    return (t + len(data)) & 0xFFFFFFFF
```

**反直觉发现**：原版 Crack 写入的 `0x005F0BEA` **经穷举验证不属于任何标准算法**（4 种输入状态 × 16 种算法变体均无法复现），而官方原版的校验和与标准算法 **100% 吻合**。

> 它能工作 ⇒ 目标程序与 Windows **均不校验该字段**。本工具改为写入**正确值**。

### 6.4 版本感知备份（防止升级后回滚点错版）

用户升级后，目录中遗留的备份仍属**上一版本**：

| 情形 | 处理 |
|---|---|
| BAK 不存在 | 直接备份 |
| BAK 版本 == 当前版本 | 保持不变 |
| BAK 版本 ≠ 当前版本，当前为纯净原版 | 旧备份归档为 `IDMan.exe.BAK.<旧版本>`，写入新备份 |
| BAK 版本 ≠ 当前版本，当前已含补丁 | **拒绝继续** |

并为「一键还原」加入**版本一致性守卫**。

> 💥 **该守卫在回归测试中当场拦下一次真实事故** —— 测试误触真实安装目录时，正是它阻止了旧版本主程序覆盖新版本安装。

### 6.5 原子写入 + 三级回滚

```
写前建 .rollback.tmp
  → 写入前 PE 终检
    → 写临时文件
      → 落盘后复读并重新解析 PE
        → 失败自动回滚
```

### 6.6 差异字节白名单

产物相对原版的**每一个差异字节**，必须落在「补丁位点 ∪ PE 校验和 ∪ 签名目录」内：

```csharp
HashSet<int> expected = ...;   // 全部预期改动偏移
foreach (int o in diffs)
    if (!expected.Contains(o)) → 判定为「意外改动」，测试失败
```
