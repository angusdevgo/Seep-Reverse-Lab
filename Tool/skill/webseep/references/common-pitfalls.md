# 常见误判与处理（v3.7.0）

遇到对应问题时读取；无需为每个任务重复背诵清单。

| 误判或反模式 | 应执行的检查 |
|---|---|
| 看到 HTTP 200 空内容就断定签名或环境错误 | 检查业务错误码、参数、权限、分页结束条件及同期成功样本 |
| 超时或 SSL 错误就断定 TLS 指纹被识别 | 区分网络、代理、证书、协议与服务端故障，做受控对比 |
| 用过期 Cookie 硬编码支撑可持续采集 | 为鉴权/动态 Cookie 定义刷新来源、失败条件和恢复方式 |
| 拿浏览器验签通过证明协议程序可独立运行 | 用 Node runtime 或实际 Python 产物在无浏览器环境回归 |
| 样本为空、expected 缺失或字段名拼错仍当通过 | 验证输入结构，每个样本至少一个有效断言 |
| 已有同站项目却从零创建替代项目 | 先读需求工作区、基线和相关 cases，再判断改版范围 |
| Hook 已注册/pending 就认定捕获成功 | 检查同 world/Frame 的 get_trace_data；未命中不构成未执行证据 |
| 源码改写成功就认定插桩运行 | 检查 runtime 标记和实际日志，再判断解析/执行失败 |
| 原生 trace 没记录就认定没读取属性 | 核对固定点覆盖、事件 cap、进程 acknowledgement 和快照语义 |
| 同 URL 多请求靠 URL 猜响应归属 | 使用 MCP v1.6.0 的请求对象关联；调用栈归因仍可能是启发式 |
| stop 立即返回就认定所有响应完整 | 指定 wait_timeout_ms 并检查 pending_requests/pending_responses/body_state |
| 将 buffer/正文截断当完整证据 | 检查 dropped_requests、body_state 和两层 truncated 字段 |
| 请求超时后无条件重放 POST | 无法证明幂等时停止并核对服务端结果，显式配置才重试 |
| 接口返回业务错误却用空列表标为采集完成 | 先验证业务状态和数据结构，成功后再推进 checkpoint |

默认失败处理：回看已有证据和 cases → 选择适合当前类型的 Hook/插桩 → 校验入口与输入输出 → 按证据调整最小环境 → 记录未解决问题。不要调用已移除的 Session/Assertion 工具，不要用强制停顿代替诊断。

验收分层：离线 fixture 回归、当前接口至少 5 次代表性请求、按业务需要追加长时间测试。没有实际跑过的时长不能写成通过。浏览器依赖是否允许以用户的交付要求为准，默认协议模式保持无浏览器依赖。
